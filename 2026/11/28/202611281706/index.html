勾了不存储照样被打开？MiniMax链接风波给开发者的教训

发表于 2026-11-28 分类于 安全 阅读次数： 本文字数： 2.6k 阅读时长 ≈ 2 分钟
Dragos 用 200 万条金丝雀测试发现 MiniMax 路由在部分不存储请求中仍打开提示词私有链接，MiniMax 回应系 B2B 安全扫描误伤并已关停，暴露出多跳路由下 ZDR 仅约束第一跳的盲区。

Hello，我是飞飞。

你平时让大模型帮忙排查线上报错时，是不是顺手就把内部文档链接、测试环境地址，甚至带着密钥的配置文件整段贴进了对话框？

为了图个安心，很多开发者还会特意在模型聚合平台里勾选一个「不存储数据」的隐私开关。大家潜意识里都觉得，只要打开了这个开关，对话发过去、结果拿回来，中间走过的数据就会像阅后即焚一样彻底消失。

可就在昨天，安全圈爆出的一份调查报告，直接把这层安全感捅破了。

美国网络安全公司 Dragos 披露，即便在明确请求不存储数据的情况下，发往 MiniMax 相关接口的提示词里，依然有大量私有链接在后台被主动打开。

两百万条测试埋出了什么

这次调查由 Dragos 首席研究官 HD Moore 牵头，周期从今年 7 月一直持续到 11 月。

研究团队用了一种安全圈常用的追踪手段，叫金丝雀链接。说人话就是往正常的测试提示词里，悄悄塞进一批只有自己知道的隐藏网址和测试账号，一旦有人在后台点开或抓取这些地址，研究人员的服务器立刻就会收到警报。

在长达几个月的测试里，Dragos 一共向多家主流 AI 服务商发送了约 200 万条带有这类标记的请求。

把数据汇总到 MiniMax 这边时，结果让安全团队直接拉响了警报。

按 Dragos 披露的口径，在路由到 MiniMax 系统的测试请求中，超过一半的隐藏链接后来都被人或程序访问过。更刺眼的是，在那些明确标记了「Zero Data Retention」（也就是零数据保留、不存储数据）的请求里，链接被打开的比例甚至达到了约三分之二。

更让外界感到不安的，是其中一个追踪案例的去向。

Dragos 称，有一条金丝雀链接在发出 24 天之后，突然出现在字节跳动的飞书聊天频道里，并且迅速被来自北京和上海的多台设备点开。此外，研究人员还监测到针对测试提示词里私有代码仓库和凭证的探测尝试。

消息一出，OpenRouter、Atlas Cloud、Novita 等几家海外常用的模型路由与聚合平台迅速做出反应，紧急暂停或调整了 MiniMax M3、M2.7 以及 M3.1 Flash 等模型端点，并公开发出警告，建议此前通过这些渠道发送过敏感网址或密钥的用户，立即把这些凭证视作已经暴露并尽快更换。

官方回应认了什么没认什么

面对外部的质疑声浪，MiniMax 官方很快发布了一份回应声明。

把双方的说法并排摆在一起看，其实非常有意思。MiniMax 并没有矢口否认「链接被打开」这件事，而是给出了一个工程视角的解释。

按 MiniMax 的说法，这起事件源于内部一套默认开启的自动化安全监控系统。当第三方商业推理路由和聚合平台（比如 OpenRouter）把 HTTP 请求转发过来时，这套安全系统会自动从流量里提取出 IP 地址和网址，记入安全日志用于威胁分析。

在后续的自动化安全排查过程中，MiniMax 内部的扫描工具和代理程序，确实主动探测并访问了日志里记录的部分网址。

不过，MiniMax 在声明里划清了两条底线：系统只提取了网址和 IP，并没有留存完整的对话内容；经过内部排查，也没有发现用户的提示词正文或模型回复被恶意泄露给任何第三方。

目前，MiniMax 表示已经关停了这套自动化安全抓取与扫描流程，停止了商业转发链路上的相关记录，并删除了已经存储的网址数据。

话虽如此，如果我们拿放大镜对照 Dragos 的报告和 MiniMax 的声明，中间依然留着一块没对齐的拼图。

MiniMax 解释清楚了「为什么后台程序会自动点开链接」，但并没有在声明里正面说明，为什么其中一条测试链接会在 24 天后流进飞书频道，又为什么会出现针对私有代码仓库的探测动作。

在没有更多底层审计日志公开之前，这部分缝隙外界暂时无法自行求证。

为什么不存储开关会漏风

把两家机构的公开声明放到一边，这件事真正值得所有开发者警惕的，是它戳穿了「不存储开关」在工程架构上的真实边界。

很多人以为勾选了零数据保留，整条数据链路就成了一根密不透风的真空管。

其实在真实的 API 调用链路里，你的请求跑完的是一场多方接力赛。

你的请求先发给 OpenRouter 这类中间聚合商，聚合商再把流量转发给下游的模型厂商，模型厂商的入口前面还挡着防火墙、安全网关和日志审计系统。

这里面最容易出岔子的，就是「管辖权」和「安全扫描」这两道暗门。

打个比方，这就像你在快递驿站寄了一箱文件，特意加钱选了「阅后即焚不留底」。驿站老板确实守规矩，转手把箱子发走、自己一张底单也没留。可包裹运到中转分拣中心时，那里的安检 X 光机为了防违禁品，自动把箱子里的网址抄下来扫了一遍。

从模型厂商的视角看，它并没有违反「不存储对话全文」的承诺，因为它觉得自己只是在安全网关层做了一次常规的 HTTP 流量威胁检测。

但从开发者的视角看，你贴在提示词里的私有内网地址、带鉴权参数的分享链接，照样被当成潜在威胁样本抓进安全日志里，甚至被自动化脚本顺着网线摸了过去。

协议里的「不存储」，往往只约束了业务层的对话落盘，很难自动穿透下游基础设施里那些默认开启的安全中间件。

开发者写提示词怎么防泄密

既然单靠勾选隐私开关挡不住下游的安全网关，我们自己写提示词和接模型接口时，就得把防线往回收到本地。

贴给模型前先做一刀占位符脱敏。 以前我用 MiniMax 语音合成接口做过一个有声书静态站项目，当时就把密钥锁在本地 .env.local 里让脚本单独读取。放到日常让 AI 排查报错的场景里也一样：把 https://internal.corp/doc?token=abc123 顺手改成 https://example.internal/doc?token=<REDACTED> 再发出去，模型照样能帮你看逻辑，就算中间哪层网关记了日志，抓走的也只是一串废字符。

核心业务尽量走直连，少经第三方中转。 跑通用问答用聚合平台图省事没问题，但一旦涉及内部排查日志或核心代码，尽量切回自己可控的官方直连或私有化环境。少跳一跳，就少一层你看不见的安全中间件日志。

用过涉事路由，直接轮换凭证。 如果你之前恰好通过第三方聚合平台调过这批受影响的模型，又往对话框里贴过测试密码、API 密钥或内网地址，别等后续调查结果了，今天就把那批密钥全部换新。

隐私开关管得住对方的数据库，管不住沿途每一道安全安检门。真正让你的内网和密钥安全过关的，是你按下回车前亲手打上的那一串星号。
