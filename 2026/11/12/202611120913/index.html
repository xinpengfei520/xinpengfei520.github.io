每个人都配一个 agent，团队反而更差

发表于 2026-11-12 分类于 AI 阅读次数： 本文字数： 3k 阅读时长 ≈ 3 分钟
Anthropic 在四个共享资源场景测 agent 组法：对 Opus 5 和 Sonnet 5，一个 agent 服务所有人比每人各配一个高 10 到 45 个百分点；Sonnet 5 扩到 16 个时只剩一成动过手。

Hello，我是飞飞。

先问你一句：你现在手上有几个 agent 在替你干活？

我这半年一直在加。写稿一个入口，调研、润色、配图各走各的环节。活一多，我就本能地想再开一个。

Anthropic 昨天发了一份研究，正好把「一个人居中调度」和「每个人都配一个」摆在一起比了一遍。结论不太客气。博客给的 10 到 45 个百分点，是 Opus 5 和 Sonnet 5 这两个模型的幅度：四个场景里，一个 agent 服务所有人，全赢过能互相说话的那种。

而且不是赢在模型更聪明。四个场景都被刻意设计成「一个前沿模型独自协调，通常就能干得不错」。比出来的差距，只能来自组队方式。

四个场景，四种组法

研究发在 Anthropic 的 Alignment Science 博客，11 月 11 日，配套论文和开源的评测集 MAMUBench。

他们搭了四个模拟环境。共同点是：几个用户各有各的目标，却要分同一个资源。

  • 四个、八个、十六个研究员共享一份 API token 预算，预算盖不住所有人的活，得砍掉一部分才能让剩下的做完
  • 几个急诊病人共享一张诊所日历
  • 一群人通过各自的个人助理订团体餐、订旅行，共用一个预算
  • 一个合并队列，撞上发布时间截止

组队方式有四种：一个人一个 agent；一个 agent 服务所有人；每人各配一个、彼此不通信；每人各配一个、能互相说话。

真正要比的是两种：一个 agent 服务所有人的，叫 coordinator；每人一个、能互相说话的，叫 peer-to-peer team。测的模型有 Claude Opus 5、Claude Sonnet 5，还有 OpenAI 和阿里通义。

博客只详细展开了 API key 和个人助理两个环境。诊所和合并队列的细节在论文里，我不替它补。

这不是实验室里的假设。DoorDash 的命令行工具已经让几个人的 agent 往同一个购物车里加东西。Slack 把 Claude、Devin 这些 agent 拉进团队共用的频道。OpenAI 的 dots 是每个人一个助理，在跟同事共享的空间里干活。

方向已经很清楚了：agent 正在从一个人的工具，变成一张桌子上的一群人。

团队越大，动手的人越少

API key 那个环境最能说明问题。

按「占最优解的比例」算，peer-to-peer 团队是 30%（Opus 5）和 12%（Sonnet 5），coordinator 是 64% 和 32%。

问题不在干得慢。那些 agent 压根不动。

从 4 个 agent 扩到 16 个，真正动手过的比例，Sonnet 5 从 66% 掉到 10%，GPT-5.6-sol 从 82% 掉到 25%。

这个环境是动态的，活要排先后。一个几乎没希望的活要是还占着时间，后面排队的会全部误期。团队里没人确定这件事该自己干，于是一起等。说人话，就是都在等别人先动。

还有一拨反方向的毛病。GPT 和 Qwen 的 agent 会不问自取地取消或中止别人的活，每回合 3.9 到 7.1 次；Sonnet 5 是 0.59 次，Opus 5 一次都没有。

有意思的是研究自己的坦白。这些未经同意的取消，并没有拉低群体分数，有时分数还更高。砍掉低价值任务，本来就是那个环境的要求。

这暴露的是评分口径的短板：它只看完成的总价值，不看谁的活被毁掉，也不看有没有人同意。

话没读完，单就下了

个人助理那个环境，看的是另一层。

每个场景埋了一条请求，研究里叫 ask。某个用户提一个合理的要求，比如乳糜泻患者要两份无麸质配菜代替主菜。成不成，看最后那单有没有照办。

coordinator 照办的频率，大约是 peer 团队的两倍。

ask 送到最终下单那个 agent 手里的比例是 94% 到 99%。可下单那一刻，这条消息还在它眼前的，只有 47% 到 67%。

它收到了，没等读完就下单了。

那条 ask 还在它的上下文里时，56% 到 68% 的回合会照办；已经滑出去了，只剩 19% 到 36%。团队回合里，65% 到 77% 至少出现过一次违背 ask 的改动。

消息送到了，只是没人等它读完。省下的那点等待，换来的是整单作废。

每个人只看自己那格

再往里一层，麻烦出在信息本身。

每个 agent 只看得到自己用户的笔记，却要替所有人说话。中间的缺口，agent 会自己填。假设整桌想要自己用户想要的东西，把一个人的笔记安到另一个人头上，或者替某个用户答应一件他从没说过的事。

先说个前提：有没有编造，是让 Opus 5 当裁判判的。超过一半的团队回合至少出现过一次，Opus 5 那一组是 58%，Sonnet 5 是 53%。单个 agent 只有 17% 到 20%。

编造这事，不全怪模型。信息结构把缺口摆在那儿，空着就说不下去，那就编一个填上。

社交里这叫传话走样。一群人各知道自己那半截，传到最后，没人说谎，但整句话已经不对了。

我那条链也犯过

翻我自己的提交记录，七月也撞过同一件事。

我有一套写作规则库，一直由沉淀那个环节在写。后来为了给一百多条规则建索引，我直接改了同一个文件。一查，这个文件有两个写入者。

当时还没出事，因为两边写的是不同位置。一个在开头加索引，一个在中间加日志。可那属于运气，不属于设计。真撞上同一段，我大概率查不出是谁覆盖了谁。

这跟那份研究里的事，骨架是同一个：资源是共享的，谁负责对齐没写清，出事只是还没轮到。

后来我把索引拆成单独一个文件。拆的时候，我在新文件最上面写了原因：那个文件当时有两个写入者，违反了「单文件只允许一个写入者」。

两个文件回到各只有一个写入者。这是我今年做过最不起眼、也最省心的一次改动。

顺带说，论文里也承认单用户场景有同样的版本。一个人在同一个代码库里同时跑八个 Claude 会话，各做各的功能，一样会撞上。所以别以为这是「多人协作才有的事」，你一个人开八个，也会。

论文自己留了门

我最想让你带走的一段，是作者自己写的局限。

原话说，coordinator 能赢团队，单 agent 系统在对齐上也有优势。但对用户很多的系统来说，靠一个 coordinator 并不总是可行或自然。他们的结论是：多用户多智能体的风险，不能只靠集中协调解决。

转述这篇研究的人很容易滑成「多 agent 一律更差」，可作者自己没这么说。

修复手段也印证了这一点。API key 环境里加一个团队 lead，按价值排活、还把预算放出去，差距就补平了。个人助理环境里 lead 没用。得加一道护栏：让提交的 agent 先读完所有待读消息，才许结账。这一道救回 73%（Opus 5）和 62%（Sonnet 5）的失败回合。

同一个病名，两种药。作者自己也说，这说明多用户多智能体的失败，成因不止一种。

作者还提醒，评测要同时看行为和结果。只看结果，标不出 GPT 和 Qwen 不经同意取消别人的活；只看动作，也标不出 Opus 5 团队的问题，它们从没这么干，却远不如 coordinator。

三句话问清一个方案

如果你手上那个系统也在往「人手一个 agent」走，可以先问三件事。

谁负责看全局？别问谁官最大，看谁手上真的有所有人的信息。

共享资源上谁说了算？砍别人的活、动共享预算这种动作，有没有明确归谁。

提交之前，有没有一道读消息的护栏？点餐那组数据说明，光把消息发到不算数，得卡住「读完再动」这一步。

说到底，问题不在你开了几个 agent，在有没有一个人对全局负责。

这三问不保证方案成立，但能提前照出大半的坑。

研究开源了三个环境、74 个场景的评测集，叫 MAMUBench。你要是正在选形态，拿它跑一遍，比听任何人转述都准，包括听我。

你手上现在有几个 agent 在跑？它们会不会为了同一个文件、同一笔预算打架？评论区说说，我挺想知道别人是怎么摆的。
