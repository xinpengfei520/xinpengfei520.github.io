别再把几十个工具裸喂给大模型了：Gemini API 终于支持动态检索工具了

发表于 2026-11-20 分类于 技术 阅读次数： 本文字数： 2.5k 阅读时长 ≈ 2 分钟
把几十个工具参数裸喂给大模型既烧钱又容易挑错。Google 推出 Tool Retrieval：用延迟加载与按需检索彻底终结工具说明书税。

Hello，我是飞飞。

如果你日常也折腾过智能体开发，或者在终端里接了一大堆外部工具，我想先问你一个非常扎心的问题：每次你哪怕只是问了一句“查下明天上海天气”，或者“看看当前分支状态”，你有没有算过，大模型在背后为了那几十个你压根用不上的工具，平白无故多读了多少字？

上周我写过一篇《59,417 对 1,421：MCP 为什么多读 42 倍》，当时用实测数据剖析过这笔账：每挂载一个工具，模型就要把它的参数说明书从头到尾读一遍。一旦你接了四五十个工具，一句话还没交代，两万多个 Token 的说明书租金就已经被扣走了。更绝望的是，因为大模型是无状态请求，对话每往前推一轮，这笔沉重的说明书租金就得一分不少地重新交一遍。

这几天，Google 在 Gemini API 的交互接口里悄悄上线了一个新特性，叫作 Tool Retrieval，也就是工具按需检索。

读完官方的技术博客，我由衷舒了一口气：大厂终于想明白了，做智能体不能再把整个五金店硬塞进模型的脑子里了。

背着五金店，又贵又易翻车

过去大半年里，整个行业在做智能体时几乎沿用了同一套惯性思维：给模型挂工具，就是把工具列表一股脑全塞进提示词上下文里。

只要你用过各种协议或者写过插件，你就会知道一个标准的工具定义到底有多冗长。每个函数叫什么名字、干什么用的，里面有几个参数，每个参数是字符串还是布尔值，是不是必填项，参数的取值范围有哪些枚举。这些细节全都要被转成结构严密的 JSON 声明，老老实实垫在每一次请求的最底端。

当你的智能体只有两三个工具时，这种做法确实简单粗暴有效。但一旦你想做一个稍微复杂一点的系统，让它既能读写数据库，又能调 GitHub 接口，还能发邮件、查日志、生成图表，你很快就会撞上三堵高墙。

最直观的痛点是账单飞涨。任务无论大小，前面都拖着一条数千甚至数万 Token 的参数尾巴，极小的操作也被平摊上了极高的固定成本。

更致命的痛点是注意力涣散。大模型并不是神仙，当候选列表里堆满了四五十个工具的详细定义时，它的上下文注意力会被严重稀释。原本该调用轻量查询的，它经常脑子一热选成了全量导出的危险接口；本来参数只要传主键的，它非要脑补出一堆可选参数。候选工具越多，选择的准确率就越往下掉。

最后是首字响应延迟被活活拖垮。每次处理输入前，模型必须先把这一大坨复杂的结构化定义全部计算一遍。

背着整个五金店上路，走得慢、花得多，还随时可能在半路上拿错扳手。

带目录出门，用时再抽手册

Google 这次在 Gemini API 层面交出的答卷非常清爽：把大模型领域早已成熟的检索思路，直接搬进了工具调用层。

实现这个逻辑的核心有两个配置项。

一个配置项叫延迟加载。开发者在注册工具或者接入远端服务时，可以给那些笨重的工具打上延迟加载的标签。一旦打了这个标签，系统在初始请求的上下文里，就只会保留极轻量的元数据，也就是这个工具的名字以及一句极短的功能介绍。至于那些占据绝大多数篇幅的详细参数类型、字段校验规则，一律留在后台待命，根本不占初始上下文的额度。

另一个配置项叫工具检索。在接口中开启这个功能后，大模型手里拿到的就像是一份轻薄的工具目录。

当用户输入具体的任务指令时，模型首先会根据语义意图在大脑里过一遍筛子：当前这个问题，到底需不需要动用专业工具？如果需要，具体对应目录里的哪一本？

当它判定需要使用某个工具时，系统会在后台以近乎零感知的速度，把那个被选中的工具说明书单独拉取出来，精准挂载到当下的推理上下文里。

这就好比过去修水管，工人必须把店里所有的锤子、电钻、气焊机全部捆在背上；而现在的做法是，兜里只揣一张工具清单，真正需要拧螺丝的时候，才回仓库把对应型号的螺丝刀取出来。

整个工具库从静态的铁板一块，变成了动态呼吸的轻量架构。

不乱前缀缓存，才算真省钱

其实在 Google 官方推出这个功能之前，业内不少做 Agent 架构的团队也动过类似的脑筋，试图在客户端自己用向量数据库做一套工具检索。

但在实际落地时，绝大部分团队都踩进了一个隐蔽的暗坑：为了把检索出来的工具喂给模型，他们习惯性地把选出来的工具声明直接拼回了最开头的系统提示词里。

这一拼，直接把另一个极其关键的降本大杀器给干碎了，那就是上下文缓存。

我们知道，现在的顶级大模型之所以能把长上下文调用的单价压得很低，核心依赖的是前缀缓存技术。只要你每次请求的最开头那一截提示词保持一模一样，服务商就可以直接复用上一轮的显存状态，给你打一个极其诱人的折扣。

如果在客户端生硬地做动态工具拼接，随着用户问的问题不同，前面挂载的工具列表每轮都在变动，前缀缓存立刻就会被彻底击穿。最后算总账，省下了一点工具参数的 Token，却把整个前缀缓存的巨额折扣全赔了进去，可以说是捡了芝麻丢了西瓜。

Google 这次在官方底层做 Tool Retrieval，最精妙的细节恰恰在于它对前缀缓存的保护。

他们把延迟加载的轻量目录钉死在系统配置的头部，保证了整个请求前缀的绝对稳定。而动态拉取出来的详细参数定义，则被规范地追加在对话链路的后半程。

既把冗余的工具说明书剔除出了初始上下文，又完好无损地保住了前缀缓存的低价红利。这种底层与机制的深度结合，才是官方下场做基础设施的真正威力。

智能体下一站，先学会减负

从最初大家小心翼翼地挂载三五个本地脚本，到今年协议生态爆发后很多人动辄接上几十个外部服务，智能体的发展经历了一段极其狂热的贪婪扩张期。

很多人总觉得工具接得越多，自己的智能体看起来就越像无所不能的超级大脑。

但现实却在一次次账单超支和参数幻觉中给我们泼冷水：如果每一个新增的能力都要付出全量上下文的每轮租金，那这种扩张迟早会被算力成本压垮。

Google 在 Gemini API 里推的这套机制，实际上给整个行业树立了一个非常清晰的方向标。未来的智能体架构，必然是分层而流动的：轻量意图感知在最外层，检索路由器在中间层，笨重庞大的参数定义在底层按需激活。

工程的真正成熟，从来不是看你往系统里塞了多少代码，而是看你在保留全部能力的同时，能把随身携带的包袱减到多轻。

当工具不再成为上下文的负担，我们才敢真正放开手脚，去构筑那些连接着成百上千项能力的复杂工作流。
