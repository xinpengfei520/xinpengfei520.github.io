切到 Opus 还差两步

发表于 2026-11-12 分类于 编程 阅读次数： 本文字数： 3.7k 阅读时长 ≈ 3 分钟
Claude Code 切模型不只是 /model opus 一行命令，官方新出的 opusplan 混合模式、Opus 5.5 默认 medium 档、子 Agent 模型继承三件事加在一起，才是真正的配置手册。

Hello，我是飞飞。

上次聊完「Opus 5.5 才是日常主力，Fable 5.2 留着打硬仗」，有朋友来问：那我怎么切？是不是 /model opus 完事？

我当时回了一句「差不多」，但事后想想，这个「差不多」差的那些，其实才是真正值得聊的东西。

这两天 Anthropic 把模型配置的文档搬到了新地址，我跟着翻了一遍，翻出了三个上次没讲到的细节。

切过去了，你在哪个档

先说一个容易被漏的事。

你敲了 /model opus，Claude Code 确实切到 Opus 5.5 了。但 Opus 5.5 默认跑在 medium 档，不是高档，不是最高档，就是 medium。

这跟你可能想象的不一样。很多人以为换了更贵的模型，它自然就更卖力。事实是，Opus 5.5、Fable 5.2、Sonnet 5.5、Haiku 5.5，四个新模型默认全是 medium。旧的 Opus 4.7 默认 xhigh，这种反差我第一次看到也有点奇怪，但想通了之后觉得设计挺合理。新模型 medium 跑出来的效果本身就已经接近旧模型的 high，拿 medium 当起点让用户按需往上调，比一开始就顶格要省钱。

官方博客对 effort 的解释让我重新理解了这件事。它不只是「思考时间」，更准确的说法是「Claude 在每一轮愿意做多少事情」：读多少个文件、跑不跑测试、做完一步之后要不要再多走几步才回来找你汇报。

medium 的意思是，这些事情做到「大部分人愿意付的程度」就停。

如果你切到 Opus 然后发现它读了几个文件就回来问你，可能不是模型不行，是档位给低了。

调 effort 的命令是 /effort。调完会弹一个滑块，s 键是只改这次会话、不保存为默认，Enter 是保存。这里有个小细节：设定会按模型分开存，Opus 5.5 存一份，Fable 5.2 存一份，你给 Opus 调高了 effort，下次切回 Sonnet 它还是用 Sonnet 自己那份默认值。互相不干扰。

有一个叫 Ultracode 的开关也在这个滑块里。它打开之后 Claude 会主动编排「动态工作流」，自动分派子任务、验证中间结果，算是比高 effort 更激进的一档。同一套代码库下如果你发现 Claude 把一件事拆成了很多步、每步都跑测试，很可能是这个开关被打开了。用 /effort ultracode off 可以关掉。

opusplan 帮你切

好，说完 effort，讲一个我觉得更好用的东西。

官方新出了一个叫 opusplan 的模型选项。

它干的事是这样的：你开始一个任务的时候，先用 Opus 5.5 跑 plan mode，把任务拆解、定路线、确定要动哪些文件。规划完了之后，自动切换到 Sonnet 5.5 来执行。

规划 Opus，执行 Sonnet。

这个设计对应了一个直觉上很容易想到但不一定真的去做的道理：规划需要判断力，执行需要速度和稳定性。贵的模型有判断力，便宜的模型够快。

有人说上次那篇讲的「Opus 比 Fable 便宜一半」已经省了，opusplan 是不是再省一半？大概是这个方向，但省多少要看你的任务结构。任务越是「规划复杂、执行机械」，这个模式越划算。如果你在跑的是完全探索性的东西，计划一边做一边变，那 opusplan 的切换时机可能不那么好卡。

用法是 /model opusplan，或者启动时 claude --model opusplan。

如果你们公司开了 Enterprise 账号有模型限制，opusplan 会自动找你可用的最高版本 Opus，所以不需要担心「设了之后结果走不到」的问题。

还有一个衍生用法。用 /model 切换会话里的模型，同时也会同步到当前会话里的子 Agent。因为子 Agent 是在你按下发送那一刻，Claude 拿你当前用的模型来启动的。所以你在开始一个大任务之前切到 opusplan，子 Agent 也都继承这套规划/执行分开的配置。

子 Agent 在跑什么模型

这一块不改，前面两件事可能都是白做的。

Claude Code 现在会开子 Agent。搜索大型仓库、批量跑测试、拿去做一堆并行的读取，这些活经常会被主任务下发给子 Agent 跑。

问题是，子 Agent 默认继承你主会话的模型。

你在主会话里跑 Opus 5.5，子 Agent 也是 Opus 5.5。你切到 opusplan，/model 切换的时候子 Agent 也同步走。

这意味着什么？搜索一堆文件、捞日志、做格式对齐这类机械活，全部在用 Opus 5.5 的 token。

官方文档里有一句话我觉得很直接：「想让某个子 Agent 跑便宜的模型，在它的 frontmatter 里写 model: haiku，不写就跟主会话走。」

如果你在搭自己的 Skill 或者 Agent 编排，这一行写进去能省不少。搜文件、捞日志、格式化输出，全部走 Haiku 5.5，主任务的判断让 Opus 拿，机械活丢给最便宜的那个。

如果你只是日常用 Claude Code 跑任务，子 Agent 是 Claude 自己决定开的，你没有 frontmatter 可以改，只能靠主会话模型来控制。

这种场景下，opusplan 的作用就更明显了：规划阶段用 Opus 做判断，执行阶段自动切 Sonnet，子 Agent 也跟着在 Sonnet 下跑，不会出现一堆便宜活全压在贵模型上的情况。

有一个环境变量 CLAUDE_CODE_SUBAGENT_MODEL 可以给所有子 Agent 设一个统一的模型覆盖，优先级比 frontmatter 低，也比 /model 低，算是最后一道默认值，自己调试 Skill 的时候可以拿来全局兜底。

什么时候升 Fable

连着两篇都在讲「Opus 比 Fable 更划算」，我怕有人误解成「Fable 完全用不着」，说一下边界。

官方博客里有个比喻我觉得说得挺好的：Fable 是专家，Opus 是资深工程师，Sonnet 是全能工程师。effort 决定他们在你这个任务上花多少时间。这三个人放在同一个问题前面，Opus 和 Fable 的差距在「见识」上，不完全在「用功程度」上。给 Opus 更高的 effort，它可以做得更仔细，但它没见过的东西，再努力也找不到线索。

Fable 值它的钱的场景，是那种任务本身就超出普通资深工程师见过的范围。跑很长的 agent session、处理整个仓库级别的重构、去排查一个边界条件复杂到需要系统性推理才能找到根因的 bug，这些是 Fable 拉开距离的地方。

官方还有一句话我觉得说得很准：「如果 Claude 把所有相关信息都给了、明显也很努力、但还是答错了，这个时候才是换模型的信号。如果它答错是因为跳了个文件没读、没跑测试、做到一半放弃了，那是 effort 不够，不是模型不够。」

把这两句话并在一起，判断流程就出来了：

错在「不用心」，先拔高 effort 档位，别急着换模型。

错在「不够用」，先从 Opus 换 Fable，别直接拔最高 effort，因为更高 effort 下 Opus 烧的 token 可能比直接换 Fable 中等 effort 更贵，而且效果还不一定更好。

我自己的记法是这样的：Claude 读文件、跑测试、走多步之前就回来找我，大概率是 effort 的问题，给它更多时间就行。Claude 认认真真读完了、也跑了，给出的答案就是对不上，这才是模型的问题。前者是工具没用对，后者是工具本身到了极限。

大多数日常开发任务，连第一步都不需要动。medium 的 Opus 能覆盖到的场景比你想象的多。

实际怎么配

说了这么多，落到操作上，我的建议是这样。

日常开发默认 opusplan。规划 Opus 执行 Sonnet，不用每次手动切，对大多数任务来说是个合理的默认值。要改默认的话，/model opusplan 然后按 Enter，下次启动就用这套。

如果发现 Claude 在执行阶段做得太粗糙，不是先升 Fable，是先用 /effort 把 Sonnet 那一段的档位拔高。很多时候问题出在「任务太复杂但模型只做到 medium 就收工」，跟模型本身关系不大。

如果你在写自己的 Skill 或者编排自己的 Agent，子 Agent 的模型要显式配。那些只是去搜索、读文件、捞日志的活，在 frontmatter 里写 model: haiku，主任务让 Opus 拿判断，机械活丢给 Haiku。这一行不写，你每次跑都在用 Opus 的价格做 Haiku 的活，省不省自己算。

真的遇到「给全了上下文还是不行」，再升 Fable。

大多数时候，你会在第二步就解决了。最不值的操作是每次遇到问题第一反应就切 Fable，每任务两块多美金，日积月累差别挺大的。
