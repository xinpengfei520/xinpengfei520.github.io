盯着AI转圈干等的人，在GEMINI.md加这四句就够了

发表于 2026-11-28 分类于 教程 阅读次数： 本文字数： 2.5k 阅读时长 ≈ 2 分钟
在 GEMINI.md 中加入动手前、每 4 到 5 步、换方向及卡住时这 4 个汇报时机，可让 Antigravity 边干活边同步进度，但规则文件仍属软约束，需控制在 200 行内并配合测试验证兜底。

Hello，我是飞飞。

不知道你用 AI 编程工具时，有没有过这种抓狂的体验。

敲完一行需求按下回车，屏幕上的光标就开始转圈。一分钟过去没动静，两分钟过去还是只看到它在读写文件。

你盯着屏幕干等，心里直犯嘀咕。它到底是在认真改代码，还是已经顺着一条错路跑偏了？

前两天我在信息流里刷到卡兹克分享的一个 Antigravity 实用技巧，办法简单到只有几行字。只要在 GEMINI.md 文件里加上一段汇报规范，规定模型在动手前、有新发现、换方向、卡住或者连干四五步时主动说一句，就能让它边做边汇报。

这招确实能立刻找回掌控感。但把规则写进配置只是第一步，搞清楚它为什么管用、什么情况下还会失灵，才不会把这几行字当成万能药。

为什么它总爱闷头干活

用过 Claude Code 或 Codex 的开发者多半有对比体感。有些工具每改几个文件，就会在界面上吐出一句人话，告诉你它接下来打算查什么。

可很多代理工具在默认状态下，一旦接到复杂任务，就会直接钻进连续的工具调用循环里。

说白了，这跟模型聪不聪明没关系，跟它的默认工作循环有关。

在多步任务里，模型每一步的思考，都会直接变成下一轮的工具调用指令。读文件、搜代码、改配置、跑命令，一环扣一环。

只要系统提示词里没要求它阶段性输出文本，模型就会把全部精力花在推进工具链上。直到它觉得活全干完了，才一次性把最终总结端到你面前。

小任务这么跑挺省心。可只要任务超过三五分钟，体验就像在盲盒里等结果。

你不知道它刚读错了哪个配置文件。你也不知道它是不是正在把一个本来只要改两行的函数，顺手给你重写了一遍。

想把黑盒拆成透明状态，最直接的办法就是在每次会话启动必读的规则文件里，给它立一个开口的规矩。

四句规则到底管用了啥

卡兹克给出的做法非常克制。他没在 GEMINI.md 里写一句空泛的「请随时汇报进度」，而是把开口时机切成了四个具体节点。

你可以直接把下面这段配置抄进项目根目录的规则文件里，或者放进全局配置中：

别小看这四条的写法，它高明在给出了明确触发器。

如果你只写一句「请多向我汇报」，模型往往会走两个极端。要么每读一个文件就给你写一段长篇大论，把界面刷得没法看。要么跑着跑着就忘了这回事，重新退回沉默状态。

把条件钉死在动手前、4 到 5 步、换方向和卡住这四个节点上，就像给黑盒运转的机械装了一块仪表盘。

动手前那一句，能让你在它刚准备改错文件时就按下暂停键。连干四五步的阶段汇报，能让你及时看清它的排查方向有没有跑偏。换方向和卡住时的停顿，更是能直接截断 AI 最爱犯的死循环试错。

我平时写博客仓库的 AGENTS.md 和项目的 CLAUDE.md 时，也有同样的体会。越是带具体动作和计数边界的规则，模型执行起来越稳；越是抽象的态度要求，几轮工具调用后就越容易被抛在脑后。

写了规则为什么还会失灵

话说到这儿，得泼一盆冷水。别以为把这四句话写进 GEMINI.md，以后 AI 就绝对不会闷头瞎跑了。

从工程机制上讲，无论是 GEMINI.md、AGENTS.md 还是 CLAUDE.md，本质上都属于提示词层面的软约束。它就像贴在工位上的一张便签，开局大家都会瞄一眼，真遇到复杂状况时，便签并没有强制拦截力。

前两天我刚在文章里拆解过 Google AI 开发者 Patrick Kelly 做的一项 470 次真实编码任务实测。

实验结果挺扎心：当全局规则和具体技能说明发生冲突时，模型在 73% 的场景里其实察觉到了矛盾，但主动开口提示你的概率是 0%。

在超长对话里，软约束被稀释的概率同样很高。之前我在用 Claude Code 配合 CLAUDE.md 时也踩过这个坑。

规则里明明写着改完代码要跑类型检查，可会话轮次一多、上下文触发压缩之后，模型照样会顺手跳过这一步。

换句话说，卡兹克这条技巧解决的是默认工作流缺少反馈的习惯问题。但它改变不了软约束的天花板。如果任务指令本身在打架，或者窗口里堆了上百轮报错日志，模型照样可能一口气跑完十几个步骤不吭声。

别让你的配置变成废话堆

既然规则文件是启动时必读的软约束，怎么把这四句汇报规范塞进去，就很有讲究。

按 Google Antigravity 官方的规则实践，GEMINI.md 本身应该是一张尽量压在 100 到 200 行以内的项目地图。以前我把冗长的常识性背景从 CLAUDE.md 里清掉后，启动上下文直接省下约四成空间。

规则越短、信噪比越高，这四句汇报规范才越不容易在长对话里被稀释。

具体到这四句本身，也建议你做两层裁剪。

只在多步骤或复杂重构任务中触发它。如果你只是让它顺手改个变量名、加个注释，还要求动手前先汇报一轮，只会白白浪费输出字数、打断节奏。

同时把汇报字数控制在两三句话以内。让它用一两行简述动作和文件路径就行，千万别让它每四步就给你写一篇小作文。

汇报再勤也替不了硬检查

最后还有一个最容易被忽略的错觉：看着 AI 边干活边汇报，觉得一切尽在掌握，就以为它交出来的代码一定没问题。

汇报进度和验证结果，压根是两码事。

模型告诉你它刚改完了三个文件、正在跑测试，这只能证明它的交互界面变友好了，不能证明代码真的编译通过了。就像对讲机里队友一直在报点，不代表前方的路障已经清空。

在日常开发工作流里，软性的提示词规则负责解决过程透明度和沟通节奏。真正决定交付底线的，永远是可验证的硬检查。

比如你在规则文件里列清楚本地构建命令、单元测试脚本和格式检查指令。或者在支持生命周期钩子的工具里，用 Hook（说人话就是工具执行前后自动触发的强制脚本）去跑类型校验。

只有这些机器能返回成功或失败的关卡，才算真正兜住了底。

这套四句规范，哪怕你现在不用 Antigravity，改个文件名放进 Claude Code 或 Codex 的规则里也一样能用。记住一条底线就够：四句汇报让你看清过程，测试和 Hook 才能帮你兜住结果。
