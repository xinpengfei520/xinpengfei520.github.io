你那个 agent 敢通宵，是因为失败变便宜了

发表于 2026-11-14 分类于 AI 阅读次数： 本文字数： 2.5k 阅读时长 ≈ 2 分钟
常驻 agent 能开起来，靠的不是模型更聪明，是单任务成本降了：官方称 Opus 5.5 在长程编码基准上每解决一个任务比 Opus 5 便宜 78%，普通任务便宜 40%；代价是原本由「贵」把守的那道闸松了，得自己补。

Hello，我是飞飞。

先问你一句：你那个跑在后台的 agent，上一次是几点醒的？

我猜你答不上来。我自己也答不上来，直到今天早上翻了一眼记录。

Anthropic 这两天发了一篇讲常驻 agent 的博客，通篇在讲怎么搭。常驻 agent，说人话就是大部分时间睡着、有事才被叫醒的那种。真正让我坐直的是中间一句话：在一个长程编码基准上，Opus 5.5 每解决一个任务，比 Opus 5 便宜 78%。普通工作负载上，这个数是 40%。

我的判断是，常驻 agent 这回真能开起来，靠的不是模型更聪明，是它每干完一件活的价钱掉下来了。判断力那条决定它能不能放手干，成本那条决定你敢不敢一直放手。

78% 是拿什么算的

先把口径摆清楚。官方写的单位是「每解决一个任务」，不是每百万 token，也不是每次调用。

这两个单位差得很远。

按 token 算，你关心的是它花了多少钱。按解决的任务算，你关心的是它有没有把活干完。前一个数会随着它多想几轮一路涨，后一个数只在它干成的时候记一笔。

官方还留了两个限定。这句话比的是 Opus 5.5 和 Opus 5，不是所有模型。那个基准只写了「一个长程编码基准」，没给名字。原文也没给每个任务具体多少美元。

这两条限定不能省，下面全建在它上面。

官方说，长程任务受益最大。常驻 agent 干的正好是长程活。一次醒来，要读文件、跑命令、改代码、再验证一遍。这种活最容易失败，也最容易重试。以前它每重试一次，你心里都要咯噔一下。

现在咯噔的还是你，只是价钱小了。

常驻 agent 的活不是一问一答。一个任务从叫醒到收工，中间要来回调很多次工具。这种活按次算，账是失真的。按解决的活算，才跟你的收益对得上。

账的单位换了

单位一换，人的动作也跟着换。

按次计费的时候，你会本能地拦着它，别试了，差不多就交。按活计费的时候，你反而愿意让它多试两轮，因为多试两轮的钱，比你自己上手便宜。

多试，本来就是 agent 干活的方式。

它不像人，看一眼就知道这条路不通。它得跑一遍，看报错，再换一条。你把它重试的次数掐掉，等于把它最擅长的那部分掐掉。

这也是我十一月十二号那篇的另一面。那天我写的是 agent 卡进死循环，每次重试都带着前面的失败记录，越跑越贵。今天说的是同一件事的另一头：一个能自己收敛的 agent，重试反而省钱。

分水岭是那条能判死的标准。测试过没过，命令跑没跑通，文件改没改对。有标准，它试几轮就停；没标准，它试到天亮也停不下来。

五个零件都在管闸

博客给了五个零件。名字先不用记，记住每个在替你管什么就行。

常驻 agent 有两个新本事：记得住，能自己动。记得住靠记忆，自己动靠定时器。剩下三个零件，都在给这两个本事上锁。

事件收件箱是门卫。外面的事先进一张表，去重，记状态。别让同一个事件叫醒两次，也别让两个执行进程抢同一件活。

定时器是闹钟。agent 自己约的下一次什么时候来，也靠它。它睡着以后，谁来叫它，归这个零件管。

记忆是交接本。每次醒来先读几个核心文件，细节按需去取。上次干到哪，它得自己接得上。

权限是一把不归它保管的钥匙。凭证放在 agent 外面，高风险的动作先过一遍分类。拿不准就把这次调用挂起，结束这一轮，等你的回复当成新事件接回来。

发件箱是投递口。要发出去的话先进一张表，再派发。一次跑完，它可以发一条，可以什么都不发，也可以挂起来等你批。没有这张表，它半夜发出去的话，你只能第二天在聊天记录里翻。

五个里，四个是闸。它们回答的是同一个问题：它半夜自己醒来的时候，谁替你把关。

贵本来是一道闸

十一月二号，我写过一篇文章，说我不打算建那层中台。

理由当时写得很清楚：我没有事件可调，我只有待办。中台真正贵的是养。十几个来源的格式会变，接口会挂，得有人一直蹲着修。

这话现在看，只对了一半。

我没写透的是另一层。贵本身是一道闸。一个任务贵，你会本能地少开、少让它自己跑。这道闸不用谁去装，价格自己就立在那儿。

价格掉下来，这道闸也跟着松了。

官方把「更便宜」当好消息写，这没问题，站在它的位置本来就该这么说。但对我这种要署名的流水线，便宜意味着我得自己补上那道原本由价格把守的闸。

十一月十二号我说过一句，给 agent 设上限，其实是给自己画一条安全线。线画了，你才敢让它夜里跑。今天要补一句：线还在，只是画线的人得从价格换成你自己。

我这十天的记录

后来我还是搭了一层，最小的一层。

到昨天晚上，里面跑着九条规则。其中一条叫「公众号·找选题」，此刻这一轮就是它叫醒的。

凌晨两点，它跑完一轮，回执里写着：点赞 3 条、评论 2 条、关注 1 个，在一条新帖下回了一句。那轮的发布配额是 0，所以它没写稿，也没发布。

那会儿我在睡觉。

数据库里这样的记录有 176 轮。171 轮跑完，四轮没活可干，一轮被取消。跑得最多的一条是 X 首页运营，88 轮，最少的只有 1 轮。中位数一轮六分四十秒，最长的一轮跑了一小时零一分半。

有三十轮落在北京时间零点到七点之间，我一次都不在场。

摆这个数，是因为十一月二号我说「我没有事件可调」。十天后，我这边有一张 176 轮的记录。

我没变勤快，也没突然多出事件可调。变的是每一轮的价钱低到我愿意让它自己跑。这个变化和那 78%，指的是同一个方向。

想搭，先算一笔钱

如果你看完也想去搭，我的建议是先别碰那五个零件。

先算三笔账。

一轮大概多少钱。别靠感觉，手动盯几轮，看实际的调用次数和费用。

失败一轮多少钱。会重试的活，成本要按最坏的情况算，不是按顺利那次算。

这笔钱谁来兜。有没有上限，超了会不会有人知道。要是半夜跑挂了，第二天早上你能从哪儿看见。

三笔账算完，再去看收件箱、定时器、权限这些零件。顺序反了，你会先搭一套很漂亮的收件箱，再发现它每晚上烧的钱你不敢看。

还有一件事得想清楚：你手上有没有稳定的活给它。没有的话，便宜也不该常驻。这是我十一月二号那条判断里仍然成立的一半。

我现在这套的卡口只有两道：选题要我点，发布要我点头。其余的交给他跑。这谈不上先进，只是我算完账之后，敢放的那一部分。

轮到你：你那个后台 agent，上一次醒来是几点？答不上来的话，今晚翻一眼记录。它比你更清楚昨晚发生了什么。
