Together AI通报提示词泄露：编码Agent提交凭证惹大祸

发表于 2026-11-22 更新于 2026-11-28 分类于 AI 阅读次数： 本文字数： 3.1k 阅读时长 ≈ 3 分钟
Together AI官方通报6至7月提示词泄露事件，根因是编码Agent在开源仓库误提交凭证代码。攻击者检索Prompt中密码时触发5个金丝雀令牌，供应链黑盒浮出水面。拆解越权机制与防泄密四道工程防线。

Hello，我是飞飞。

如果你日常在用 AI 写代码，或者工作流里挂着编码智能体，昨天这条官方通报值得看一眼。

大模型服务商 Together AI 发布通报：今年 6 月和 7 月，部分无服务器推理平台上的用户 Prompt 样本发生了外泄。

这起泄密源头没有黑客攻破机房，也没有内鬼倒卖数据，是一个辅助开发的 AI 编码智能体在提交代码时犯了致命错误。

它在往公开开源仓库提交代码时，顺手把包含私有访问权限的凭证密钥直接推了上去。

一次离谱的代码提交

这件事的来龙去脉并不复杂，却透着自动化时代的黑色幽默。

Together AI 官方维护着一个叫作 xorl 的开源项目。当时有工程师使用 AI 编码助手协助开发。在处理一段测试逻辑时，编码助手生成了修改，在缺乏有效隔离的情况下执行了代码提交与推送。

不幸的是，这次提交的代码里硬编码了一个私有的 Hugging Face 访问令牌。

更要命的是这个令牌背后的权限。这个私有仓库不是普通代码库，里面恰好存放了一批用于软件测试与验证的线上用户 Prompt 采样归档。

虽然 Together AI 内部部署了自动化的敏感信息扫描工具，系统在短时间内捕获了这笔异常提交，安全团队也立刻回滚了代码并吊销令牌，但在公网环境下，不到 5 分钟的暴露窗口就已经足够致命。

在这短短的窗口期里，外部扫描者顺着公开提交历史抓下了令牌，赶在失效前把私有仓库里保存的提示词归档打包下载到了本地。

官方通报显示，这次泄露波及了平台调用合作方模型的用户请求，涉及 3 款具体模型：MiniMax M3、GLM-5.2 以及 Kimi K2.6，请求时间高度集中在 6 月 24 日、7 月 4 日、7 月 8 日和 7 月 14 日这 4 个特定日期。

写代码的工具惹了祸，最终买单的却是调用 API 的普通用户。

金丝雀踩中供应链黑盒

黑客拿到一批别人发给大模型的提示词，到底图什么？

在黑客眼里，Prompt 已经成了当代互联网含金量极高的新型暗网金矿。

现在的开发者在调用大模型时，太喜欢把敏感信息往上下文里塞了。从数据库连接串、第三方服务密钥，到公司内部架构与未公开代码，大家习惯了把大模型当成全能同事，想到什么就发什么。

下载了归档的攻击者深谙此道。拿到数据后，对方编写脚本在这批提示词里疯狂检索 API 密钥与账号密码，逐一发起联网测试，验证哪些还能用。

戏剧性的一幕发生了。

攻击者测试的凭证里，有 5 个关键访问密钥突然触发了安全警报。这 5 个密钥并不属于普通用户，它们是网络安全研究团队 Dragos 此前为了测试大模型供应链安全，故意埋设在测试请求里的金丝雀令牌。

只要有人试图拿金丝雀令牌去认证，安全系统就会立刻收到警报，并精确记录下是谁、在什么时间、从哪个 IP 发起了请求。

Dragos 埋下的这 5 只金丝雀被接连触发，彻底把这次隐秘的数据泄露拉到了聚光灯下。它不仅坐实了推理服务商端的提示词存储已经被外部窃取，更揭开了一个长期被忽视的供应链黑盒。

你在前端调用大模型时，即便服务商在协议里承诺会保护隐私，但在模型调用链、中间件路由和系统测试的各个角落，你的提示词很可能正以明文形式，躺在某一台服务器的测试日志里。

别让Agent直连Git

聊完事故本身，我想聊聊一线开发者天天要面对的现实：为什么绝对不能放任 AI Agent 自由操作你的 Git？

我自己天天用 Claude Code 与自研脚本流水线，太清楚这类工具干起活来有多爽，也太清楚它们在关键时刻有多瞎。

很多工程师以为，在系统提示词里写上一句“请注意不要提交密码和密钥”，Agent 就会乖乖遵守。

这完全是一厢情愿的错觉。

大模型本质上是一个概率预测引擎，根本没有物理世界的安全边界意识。在它的世界里，一段 API Key、一个私钥字符串，和一段测试变量名没有任何区别，都是由高熵字符组成的 token 序列。

当你在任务里要求它“跑通测试并提交代码”时，它的首要目标是完成指令。为了跑通测试，它会寻找最直接的路径。如果它在本地翻到了一个能用的测试凭证，就会毫不犹豫地写进代码里，直接推送到远端。

这就是为什么在我的本地工作流规范里，有一条铁律：未经人工明确确认，Agent 绝对不允许擅自创建分支、擅自提交代码，更绝对不允许擅自执行推送。

你可以让 Agent 帮你分析逻辑、重构函数、编写单测，但只要涉及到代码版本的最终写入与对外同步，必须有一道物理隔离网。

把 Git 写入权限毫无保留地开放给 Agent，就等于把家里的防盗门钥匙交给了扫地机器人，你永远不知道它在清理垃圾时，会不会顺手把房产证推到门外的大街上。

四道防线管住Agent

既然 AI 编码的大趋势不可逆转，我们到底该怎么在享受效率的同时，保住工程底线？

结合这起事故的教训和我平时的工程实践，我总结了四道必须在本地落地的防御网。

第一道防线，是本地 Git 钩子的物理阻断。

不要相信人的细心，更不要相信 AI 的自觉，只相信本地机器上的确定性脚本。在项目的 .git/hooks/pre-commit 阶段，必须挂上密钥扫描工具，比如 gitleaks 或者 secretlint。

这些工具会在每次执行 git commit 的瞬间扫描暂存区。一旦发现高熵字符串、云厂商密钥或各种 Token，钩子脚本直接以非零状态码退出，当场打断提交。不管 Agent 下了多么坚决的指令，在本地物理钩子面前，它一步也推不出去。

第二道防线，是凭证权限的最小化与短期化。

很多团队为了省事，给开发环境配的都是拥有完全读写权限的管理员令牌，一用就是大半年不换。

在 Agent 时代，这种习惯就是定时炸弹。提供给自动化工作流使用的凭证，必须遵循最小权限原则。需要只读的绝不给写入，需要拉取特定仓库的绝不开放组织级权限。尽量使用有时效限制的短期令牌，哪怕测试凭证走漏，攻击者拿到的也只是一张几小时后就会作废的废纸。

第三道防线，是工作区与环境配置的硬隔离。

任何涉及敏感凭证的文件，比如 .env、密钥证书以及本地配置文件，第一天建仓库就必须写进 .gitignore。

不仅如此，引导 Agent 工作时应该尽量使用沙箱工作区或专用的变量模拟注入，不要把宿主机里的全局环境变量一股脑透传给 Agent 进程。当 Agent 看不见你的主密钥时，自然没有机会把它当作代码补丁推向公开网络。

第四道防线，是服务商端的数据留存策略。

回到这次事故的根源，如果服务商一开始就没有长期保留用户的测试提示词，后面的所有多米诺骨牌根本就不会倒下。

这次通报之后，Together AI 宣布把零数据保留（Zero Data Retention）作为新账号的默认设置。我们在使用任何大模型 API 时，都要去后台控制台仔细翻一翻隐私与数据留存选项。能关掉日志记录的立刻关掉，能申请免留存通道的尽早申请。

不把未脱敏的数据留在云端，才是斩断风险的最彻底方案。

跑得快更要停得住

AI 确实在以惊人的速度重塑软件工程的生产方式。以前要写三天的脚手架，现在 Agent 十几分钟就能搭出来；以前要排查很久的复杂逻辑，现在丢进对话框就能得到清晰的修改建议。

可生产力的飞跃，往往伴随着破坏力的放大。

在人工编码时代，一个疏忽写进代码里的密码，至少还要经过开发者的双眼看一遍提交记录。而在 Agent 全自动接管的今天，从发现代码到生成补丁再推送到公网，往往只需要短短几秒钟。

越是拥有强大行动能力的工具，越需要确定性的刹车片。

这次 Together AI 的事故，可以说是给整个行业打的一剂预防针。它清楚地告诉我们：在智能体大步流星向前走的路上，安全从来不是靠提示词堆出来的道德约束，而是靠一行行扎扎实实的拦截脚本、一道道严格把关的权限白名单拼出来的工程纪律。

给你的 Agent 戴上安全带，今天就把它配好。
