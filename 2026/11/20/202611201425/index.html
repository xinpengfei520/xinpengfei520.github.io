告警响了别呼叫人类：OpenAI 怎么让 Codex 自己排障提 PR

发表于 2026-11-20 更新于 2026-11-28 分类于 技术 阅读次数： 本文字数： 2.9k 阅读时长 ≈ 3 分钟
OpenAI 披露内部性能工程体系：三个月内用 Codex 自动完成 1700 次调查、定位 600 个根因，用全天候流水线取代人肉值班排障。

Hello，我是飞飞。

不知道你有没有经历过这种被支配的恐惧：大半夜两点钟，手机突然像催命一样疯狂震动，报警群里弹出一条延迟暴涨十倍的报警信息。

你只能揉着眼睛爬起来打开电脑，深吸一口气点开监控大盘。接着就是长达两小时的痛苦折磨：一边在微服务里翻链路追踪，一边在几百条提交里排查，试图揪出到底哪行代码导致了内存泄漏或死锁。

这种事经历一次，就能让人少活一年。但在软件工程被 AI 深刻重塑的今天，折磨正在呈指数级加剧。以前团队一周合几十个 PR 就算高产，现在有了编程智能体加持，代码迭代速度翻了十倍不止。当写代码的速度坐上了火箭，负责兜底找性能问题的工程师却还在靠人肉看日志，崩溃只是时间问题。

昨天 OpenAI 罕见地复盘了他们内部的一套秘密武器，名字叫 Performance Factory。他们没有把更多的排障责任压在人类值班工程师身上，而是把 Codex 放进了全天候流水线。三个月下来，这个系统自动完成了 1700 多次故障排查，精准定位了 600 多个根因，甚至还直接写好提交了几十个修复代码。

半夜被叫醒是每个人的噩梦

搞微服务或者高并发系统的人都清楚，线上真正昂贵的从不是监控探针，高级工程师的精力和睡眠才是最顶级的消耗品。

现代系统的监控体系已经非常敏锐了。从端到端耗时、错误率到垃圾回收的停顿时间，任何微小的抖动都能在毫秒级被探针捕捉到。可问题恰恰出在这里：监控系统只负责吹哨，它从来不负责破案。

当一条警报在工作群里炸开时，留给人类的只有冰冷的一行指标异动。到底是刚刚发布的新接口把下游连接池打满了，还是某位同事漏写了索引，亦或是上游依赖在超时重试？要搞清楚这些，工程师必须在几十万行日志里捞蛛丝马迹，像法医勘查现场一样一点点拼凑线索。

更让人头疼的是性能回归。它不像直接抛出异常崩溃那么直观，系统可能还在正常跑，但处理单次请求的耗时悄悄从 200 毫秒涨到了 400 毫秒。这种慢性失血的问题排查难度极大，往往需要拉齐三四个业务模块的同学一起对账。

OpenAI 在这篇复盘里说得很直白：当智能体让整个团队的开发吞吐量暴涨时，传统依赖人类轮流值班查日志的模式，已经彻底沦为了生产力瓶颈。

既然代码是智能体辅助写出来的，那排查性能问题的苦活累活，也必须由智能体来接盘。

现场勘查交给化验室跑腿

OpenAI 设计这套被称为 Regression Workflow 的流水线时，最精明的一点在于他们完全重构了报警的响应链条。

在传统的体系里，告警的第一站是人类。值班工程师收到通知，打开电脑开始当肉肉搬运工。但在 OpenAI 的这套体系里，告警响了之后，现场被直接封锁并移交给云端的 Codex 智能体。

这就好比医院急诊科。病人被推来的时候，主任医师不需要亲自去给病人抽血、拍片子、化验各项指标。门口有一个全天候运转的自动化化验室，在警报拉响的第一秒，化验室就已经自动去提取病人的各项生化指标，把打印好的诊断依据和异常切片整整齐齐地订在病历夹上。

Codex 扮演的正是这个急诊化验室的角色。

一旦线上监控探针发现 ChatGPT 的某项延迟指标偏离了正常轨道，系统会自动在内部追踪平台生成一张工单。与这张工单绑定的云端 Codex 实例瞬间启动。

它首先会读取触发告警的遥测数据，沿着分布式调用链路把上下游相关的日志包全部抓取下来。紧接着，它会对比该时间段内所有服务的部署变更历史，一条条翻看最近的 Git 提交记录。甚至在权限允许的沙盒环境里，Codex 还会尝试用当时的请求特征去复现那次慢查询。

这一套动作做完，通常只需要几分钟。此时人类工程师还没来得及倒上一杯咖啡，工单里就已经附上了 Codex 整理好的现场勘查备忘录：具体是哪一次代码变更、涉及哪个函数、在什么特定参数组合下会引发性能瓶颈。

找第二个模型挑刺当辩友

让 AI 去看日志找根因，很多人的第一反应是：这玩意会不会胡思乱想？

搞过大模型排障的同行都有过惨痛教训。模型在面对海量混乱的日志时，很容易把两个偶然同时发生的事件生搬硬套在一起。比如刚好有个网络抖动，又刚好有位工程师合了一段前端重构，单智能体很可能会一口咬定是前端重构把后端数据库拖垮了。

修代码最忌讳的就是病急乱投医。如果让一个带着偏见或者幻觉的 AI 去提修复方案，后果可能比原本的性能回退还要严重。

OpenAI 在这里加入了一道极其硬核的工序：对抗性审查。

当负责调查的 Codex 给出一份看似天衣无缝的根因分析报告后，系统并不会直接采纳，而是立刻拉起第二个独立的对抗性智能体，充当它的反方辩友。

这个反方智能体的唯一任务，就是专门挑刺。它会拿着第一位 Codex 的诊断结论，去反查原始的遥测指标和调用堆栈，寻找逻辑漏洞。它会严苛地质问：你说是这段循环导致了 CPU 飙升，但为什么同时段另一台没有这个更新的机器也发生了类似抖动？你说是锁竞争，那相关的线程等待堆栈在哪里？

如果在这种背靠背的交叉审讯中，初版诊断露出了破绽，整张工单就会被无情打回，要求 Codex 补充证据重新调查。

只有当证据链足够扎实、完全经得起反方辩友的盘问时，Codex 才会获准进入下一步，针对瓶颈代码生成对应的修复代码并提一个 Pull Request。

这种把两个模型放在对立面相互制衡的思路，直接把排障归因的虚假率压到了极低水平。

体温计降了才准签字关单

有了精准的根因分析，也有了生成的修复代码，是不是就意味着系统可以高枕无忧了？

并没有。在 OpenAI 的工程底线里，任何没有经过线上客观指标验证的修复，都只能算作未决的草案。

这就引出了流水线的最后一道把手：人类审核与闭环验证。

Codex 生成的所有修复 PR，永远不会被允许自动合入主分支。它会被推送到负责该业务模块的人类工程师面前。工程师此时拿到的是一份极度精简的成果物：一边是经过对抗审查验证的现场证据，另一边是改动范围极小的修复补丁。人类只需要把精力聚焦在最后十秒钟的业务判断上，确认逻辑无误后点击合并。

但合并上线并不意味着结案。

这就像医生开完药给病人吃下去，绝不能在药刚吞下去的那一秒就宣布痊愈。必须拿出体温计，盯着水银柱真的从 39 度退回到了 36 度半，病人才准办出院手续。

在补丁部署到生产集群后，流水线会派出第三个验证智能体。它在后台紧盯着实时的大盘数据，持续观察半小时到一小时。它要亲眼看到那条原本翘尾巴的延迟曲线重新落回健康水位，并且没有诱发新的错误码，才会在工单上盖上通过印章，正式结案关单。

这套把人类从繁琐排查中彻底解脱出来的系统，在运行的头三个月里交出了惊人的战报：日均处理 17 次复杂调查，成功定位 600 多个隐蔽故障，推进了 400 多起针对性修复。

过去很多团队都在争论，AI 时代到底还需要不需要 SRE，代码智能体到底能不能碰生产环境。OpenAI 这次用一套严丝合缝的闭环工程给出了示范。

智能体最迷人的地方，从不在于让它脱缰狂奔。关键在于用代码和规则把它框进最繁琐、最枯燥的流程里，让它当一个不眠不休的现场法医，在人类签下名字之前，把所有证据链都钉得死死的。

你平时在线上遇到性能回归或者排查故障时，最耗费时间的是哪一步？如果让 AI 智能体帮你排障甚至提交代码修复，你最担心的又是什么？欢迎在评论区聊聊你的实战体验。
