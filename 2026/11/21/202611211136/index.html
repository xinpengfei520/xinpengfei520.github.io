给智能体一张设计图根本不够：Figma 怎么用画布把全部上下文接进代码

发表于 2026-11-21 分类于 AI探索 阅读次数： 本文字数： 2.8k 阅读时长 ≈ 3 分钟
很多人以为大模型写不好界面是视觉能力不行，但一线开发都知道真正的断层在上下文。Figma 推出 Specs 与 MCP 闭环，把散落在 4 个系统的文档、数据和原型全部打包，交给编码智能体。

Hello，我是飞飞。

如果你最近也经常让智能体写界面，大概率踩过这样一个坑。

你把精心画好的设计稿截图丢进对话框，或者把网页设计链接甩给模型，让它照着写个前端页面。模型唰唰吐出几百行代码，跑起来乍一看挺像那么回事。但只要你上手点两下，或者往现有工程里一塞，整个人立刻就清醒了。

间距和配色全是写死的，团队维护两年的设计规范组件一个没用上。按钮除了默认态，悬停、禁用、加载态全靠模型自己猜。更不用说页面背后的业务逻辑了：数据从哪来、异常状态怎么兜底、特定交互规则是什么，模型通通两眼一抹黑。

很多人把这种翻车归结为模型视觉能力还不够强，或者是推理能力有欠缺。但在真实工程里待久了你就会发现，真正卡住智能体的从来不是语法，而是上下文压根没给全。

Figma 这周在工作流实验室里放出了一个技术闭环演示。他们把刚公测的 Specs、在画布上直接运行的 Code Layers，以及承上启下的 Figma MCP 串在了一起。看完整套流程，我最强烈的体感是：大模型写代码的最后一公里，终于有人摸对了方向。

真正断掉的是上下文

先退一步看我们平时是怎么做开发的。

稍微正规点的需求，信息从不可能呆在同一个地方。需求文档写在云笔记，数据看板挂在分析平台，流程图画在白板上，设计规范躺在设计软件里，代码和用例又落在代码仓库中。

一个成熟的人类工程师之所以能把功能写出来，关键不在敲代码的速度，而在于他在这些分散系统之间穿梭的经验。他得去问产品特定分支怎么走，去查看板看功能给哪个城市的用户用，再去翻设计规范确认卡片该调哪个现成组件。

换到智能体身上，我们却往往指望它靠一句提示词和一张静态图片就把所有事情办妥。

这就像把一个新来的实习生关在小黑屋里，只从门缝塞给他一张页面截图，就要他在半小时内把连带后端接口和完整状态机的生产级代码交出来。他不写出幻觉才怪。

代码生成发展到今天，基础的组件拼装和语法生成早就被攻克了。阻碍智能体进入生产环节的最大鸿沟，正是这种严重的上下文断层。

为什么只给截图总是写废

截图之所以不够用，是因为静态图片能承载的信息密度实在太低了。

一张设计图展示的只是某一个瞬间的视觉切片。但一个真实组件在系统里运行时，至少连着三个维度的隐性知识。

其一是交互与状态机。一个输入框在获得焦点、输入中、校验报错、网络超时甚至只读模式下分别长什么样，静态截图给不出来。

其二是数据源与契约。页面上的列表是假数据还是真字段，分页怎么做，排序规则是什么，截图上面同样是一片空白。

其三是设计规范复用。团队在库里封装好的通用按钮、弹窗和布局容器，截图里看起来只是普通色块。模型没有规范的映射关系，只能每次用最原始的标签和行内样式重新拼一遍。代码越积越多，整个项目的技术债迅速堆成高山。

这些东西全被截断在图片之外。当你只给模型提供视觉切片时，模型就只能在盲区里自行发挥，最终产出的往往是能看不能用的演示玩具。

把散落的事实钉回画布

Figma 给出的解法挺有意思。他们没有试图去改造外面的各种大模型，而是先从自己的画布动手。

所谓 Specs，本质上是一个以 Markdown 为载体的画布容器。以往需求归需求、图归图，工程师要在浏览器标签页之间来回横跳。现在 Specs 允许团队直接在设计稿旁边开辟一块结构化的文档区域。

在这个区域里，你可以直接把产品的业务指标拉进来。比如在官方演示中，团队要上线一个配送试点功能，但在哪个城市首发还没定。以往工程师得跳去数据分析平台查使用量，再跑回设计稿里对齐。

而在新流程里，工程师通过连接器直接在画布里调取业务数据，让智能体在画布上自动生成包含订单量和使用密度的统计表格。

技术方案、系统架构图以及设计团队给出的文字标注，也被规范地整合在同一块画布上。所有的业务决策和上下文被摆在了界面的正旁边。

这就把原本散落在各个孤岛里的碎片事实，重新钉死在了一个统一的共享空间里。

让原型里跑着真实代码

光有文字描述还不够，动态交互历来是设计向开发交付时最大的灰色地带。

Figma 在这次工作流里重点推了 Code Layers，也就是代码层。以前我们在设计软件里做的原型，哪怕连线连得再复杂，本质上依然是画面帧之间的跳转。真实环境里的动态响应、组件动效和数据绑定，在原型里全靠口头传达。

而代码层直接把能够真实运行的前端代码塞进了画布。

在演示里，工程师为了展示地图标记点缩放时的聚合动效，直接在画布上放了一个跑着真实代码的交互地图。

这意味着不仅人类能看到实际的运行效果，智能体在读取这个原型时，接收到的不再是模糊动图，直接拿到了带行为定义、带参数配置的实际代码。

当业务数据、技术说明、视觉规范和运行代码全部汇集在画布之后，工程师选中这套上下文，让 Figma 内置的智能体运行预设好的实现计划生成技能。

这个技能把所有输入揉合在一起，吐出了一份端到端的实现计划。里面涵盖了视觉呈现、边界行为、埋点要求，以及详尽的任务拆解清单。

一根链接牵出全部上下文

写出计划只是前半程，关键在于如何把这份计划交接给终端的编码智能体。

如果换成过去的思路，我们大概率要把这份计划复制粘贴成一段巨型提示词，或者到处导出文件打包传给 Codex 或 Claude Code。这种做法既费时又容易丢失深层关联。

Figma 这里的关键一步，是把这一切接进了官方的 MCP 服务。

工程师在画布上右键复制这个 Spec 计划的分享链接，转身切到终端里的 Codex，敲下一句简单的指令：实现这个功能，后面附上刚才的链接。

Codex 并没有仅仅把那串链接当成纯文本网页去爬取。它通过配置的 Figma MCP 服务，顺着链接直接穿透到底层的画布数据树。

智能体顺着这根管道，不仅一口气读完了 Markdown 格式的技术计划，而且自动拉取了关联的设计标注、代码层中的实际交互逻辑，以及设计规范库里现有的组件元数据。

以前我们在对话框里反复叮嘱的组件名、尺寸变量、间距规范，现在被 MCP 协议封装成精确的上下文，原生喂给了正在写代码的模型。

模型在生成代码的每一秒钟，手里握着的都是最完整、最精确的上下文地图。

谁在替最终的代码兜底

看完整套演示，我最大的感受是：智能体写代码的分水岭正在悄悄发生变化。

过去一年多，大家都在卷底座模型的参数量、卷谁的基准跑分又高了几个点。但真正把代码落地到生产工程里的团队都在慢慢醒悟：模型本身的能力固然重要，但决定产出质量上限的，永远是你能喂给它多干净、多结构化的上下文。

MCP 协议在这类场景下的价值被体现得淋漓尽致。它跳出了普通查天气小插件的玩具定位，把像 Figma 这样复杂的生产力工具内部的数据富矿，以标准协议开放给外面的智能体消费。

不过在兴奋之余，我也想提醒一句：这条路并不意味着从此人人都能翘着二郎腿一键出代码。

当上下文的传递变得极度顺畅，新的压力反而转嫁到了前期的上下文治理上。如果你的产品需求本身自相矛盾，如果你的设计画布缺乏规范、图层乱作一团，智能体通过 MCP 抓取到的就只会是一堆放大了数倍的混乱。

工具链可以帮我们把桥搭好，但桥上流淌的数据质量，永远考验着人类团队最底层的工程素养。
