半个月前我说它还不算开源，今天腾讯把 224B 权重交出来了

发表于 2026-11-18 分类于 AI 阅读次数： 本文字数： 2.5k 阅读时长 ≈ 2 分钟
腾讯混元正式开源 Hy4 flash 权重，224B 参数包含 64B 记忆模块，激活参数仅 12B，支持 1M 上下文。对比两周前计划开源的质疑，这篇算清 224GB 显存容量与极低推理成本的选型账本。

Hello，我是飞飞。

两周前，腾讯混元发布 Hy4 正式版的时候，我在文章里留了一段挺不客气的话。当时官方新闻稿里写着计划开源模型权重，我跟读者说，计划这两个字得打折，权重没放出来之前它只是个云端服务。能不能拿走，要等权重放出来才算数。

话音刚落十四天，腾讯没拖延，今天真把权重推上了 Hugging Face 和 GitHub。

如果你这段时间也在盯开源模型的动态，大概会注意到社区里的一阵骚动。这次腾讯没拿缩水演示版糊弄人，直接把完整的 Hy4 flash 权重端了上来，包含 Base 基座、指令微调版和 FP8 量化版本。很多两周前还在观望的开发者，今天一早都在问同一件事：这块两千多亿参数的开源大模型，到底能不能搬回自己的本地机器上跑？

先别急着去终端里敲下载命令，咱们先算算这笔真实的物理账。

这次交出来的到底是什么

把 Hugging Face 上的模型卡片翻开，这次混元交出来的底牌有几个很扎实的数字。

总参数量大约 224B，也就是 2240 亿参数。里面包含了一个叫 Engram 的条件记忆模块，占了 64B 参数。但最核心的设计在于它的计算激活：单 token 实际激活的参数量，只有 12B。

架构上它走的是混合专家网络，加上混合注意力和潜变量 MoE。用大白话讲，它在平时待机的时候，脑子里装着两千多亿参数的知识体系；可一旦真正开始算某一个字，它只调动其中不到二十分之一的神经元去干活。这种设计把单步计算的开销压到了极低的水平。

更关键的是两条生产力指标。一个是 1M 的原生上下文，相当于一次能吃下上百万字的中文材料或者数十张高清图表；另一个是原生多模态，输入端直接接受文字和图像混合排版。

生态适配这次也没让人猜谜。开源当天，官方在仓库里直接给出了 vLLM 的一键拉起命令。只要环境配好，打一行命令就能把一个兼容 OpenAI 格式的本地推理服务跑起来。

但有一处细节跟之前很不一样。早先的 preview 版本用的是极其宽松的 Apache 2.0 协议，而这次正式版权重换成了腾讯专属的 Tencent Hy License。这意味着你可以免费下载、学习和部署，但在涉及大规模商业应用或者对外提供商用服务时，得遵守具体的授权条款。这跟 Meta 的 Llama 协议类似，是属于大厂特有的开放权重规则，而不是毫无约束的纯粹开源。

224B 背后的那道显存墙

很多朋友看到 12B 激活这几个字，第一反应是：这不跟我手里的轻量模型差不多大吗？我电脑里的显卡是不是终于能跑 2000 亿大模型了？

这恰恰是 MoE 架构最容易让人产生幻觉的地方。

咱们把账拆开来看。模型的参数有两种存在形式：一种是静止躺在硬盘和显存里的容量，另一种是跑起来参与浮点运算的计算量。

12B 指的是计算量。因为每次只有 120 亿参数参与计算，所以它跑起来的速度极快，延迟很低，每秒吐字数能逼近小型模型。

但那 224B 的总参数，在推理服务启动的那一瞬间，必须完整常驻在显存里。即便是官方做好的 FP8 量化版本，每个参数只占一个字节，2240 亿参数也需要实打实吃掉大约 224GB 的显存容量。

224GB 显存是什么概念？

你手里要是有一张 24GB 显存的消费级旗舰显卡，比如 RTX 4090，你连它的零头都塞不下。哪怕你在主板上插满 4 张 4090，显存加起来也只有 96GB，依然连半个模型都装不进去。要想把这个 FP8 版本的权重完整拉起来，你起步就得准备 4 张 80GB 的专业计算卡，或者 8 张 4090 做更高强度的量化切分。

这道显存墙把想要在个人电脑上尝鲜的个人开发者挡在了门外。

它用 224B 的体量保证了长文本检索的稳定性和多模态理解的上限，却也天然注定了它的归宿：它不是给个人 MacBook 准备的玩具，它是一把专门为企业私有集群和算力中心打造的重型工具。

这块肉到底该切给哪类活

算清了物理成本，接下来的问题就很实在了：既然个人本地跑不起，腾讯把这个权重放出来，对我们这些一线开发者到底有什么用？

我自己的秤从来没变过：看错一次的代价有多大，一天要跑多少次，乘上实际的单价。

按这个标准，Hy4 flash 这次开放权重，真正能啃下的是两块过去极其尴尬的硬骨头。

先说企业内网的私有化落地。

在很多中大型企业里，客户数据、内部财务日志、未公开的核心代码库，哪怕云端 API 降到不要钱，安全合规部门也绝对不许向外网发一个请求。过去企业要想自建，要么选几十 B 的开源模型，知识储备和推理深度经常不够用；要么咬牙去布上千亿的密集模型，硬件采购成本直接上千万。

Hy4 flash 给出了一个很折中的解法：硬件上你只需要堆出容纳 224GB 权重的显存池，而日常并发运行时的算力消耗却只有 12B 的级别。这意味着一台多卡服务器可以支撑起比以往高得多的并发吞吐，同时把 1M 长文本和图表解析能力稳稳锁在企业内网里。

另一块是长上下文的高并发 Agent 流水线。

天天用大模型跑自动化流程的人都清楚，流水线里最贵、最拖慢速度的不是写那几句最终结论，而是前期的海量上下文搬运。系统 Prompt 塞上几千字，长文档和错误日志倒进去几万字，多轮交互下来，上下文窗口迅速膨胀。

如果用传统的密集模型，哪怕上下文再长，几十轮对话下来延迟就会直线上升。而 Hy4 flash 引入的 Engram 条件记忆技术和 LatentMoE 架构，本质上是在做一件极其克制的事：在长上下文里动态压缩记忆开销，只唤醒跟当前问题相关的局部专家。

它适合接的是那种高频、量大、吞吐密集、但规则边界清楚的活。比如把一个大型历史仓库的所有代码全量吃进去理清依赖，或者对数万条客户工单做多模态图文分类。

至于复杂的架构设计、深度的逻辑推导，我依然会把钥匙交给最前沿的闭源旗舰。国产开源模型在这个阶段最迷人的地方，恰恰是它把原本高不可攀的技术做成了廉价好用的零件。

两周前腾讯说计划开源，我泼过冷水；今天它把 224B 的权重真金白银推到众人面前，这份兑现承诺的执行力值得一句肯定。门槛虽然挪到了显存容量上，但能拿走的东西，决定权终于交回了开发者自己的手里。

要是你手头也有需要私有化部署或长文本处理的业务，不妨算一算：如果把现有的高并发接口切到这种大容量、低激活的 MoE 架构上，你的显存账面和响应速度到底能拉开多大差距？欢迎在评论区聊聊你的测算结果。
