Claude 写九成代码，验收标准却不由它改

发表于 2026-11-17 更新于 2026-11-19 分类于 编程 阅读次数： 本文字数： 3k 阅读时长 ≈ 3 分钟
Claude Code 团队约九成代码由 Claude 写，敢合进去靠的是把验收标准放在改动碰不到的分支、三轮不过就交给人，内部一轮通过率从 65% 升到 78%。

Hello，我是飞飞。

先说一件我到现在还记着的事。你要是也在让 agent 自己提代码，大概率踩过类似的坑。

去年冬天，我那条内容流水线的每一步都在打勾。构建过了，检查过了，屏幕上全是绿的。真正出事的是最后一步，推代码的认证悄悄红了。整条链路挂了一整天，没人发现。那一天，本该自动跑完的活一步也没往前走。第二天我才看到。

那天的绿灯不是假的，它只是只亮了一半。检查跑完了，可没人检查「检查有没有真的跑完」。

昨天我写过 Claude Code 那个 exit 2 的钩子，说的是单点的一道闸。大前天写过给活造裁判，说的是怎么判断一件事干得好不好。这两样都还是零件。真正让一个团队敢把九成代码交给 Claude 的，是把这些零件装成一条能自己转、也停得下来的验收流程。

Anthropic 11 月 16 日发了一篇工程文章，作者是 Addy Osmani。开头第一句就把问题摆出来了：Claude Code 团队大概九成的代码由 Claude 写，也由 Claude 审。那谁在保证它不塌？

他们的答案不在「模型更强了」，在验证循环。

敢并行的前提

文章里有一句话，我觉得比那个九成更值得记。没有验证循环，你同时只能跑一两个 Claude；有了它，才能跑几十上百个。

敢并行不是胆子大，是检查便宜到可以天天跑、自动跑。你手上那条流水线如果每加一个 agent，你就得多盯一屏，那它还没到能并行的程度。

我更关心后半段：它写完以后，团队拿什么接住。九成这个数字只是结果，流程才是原因。

绿灯为什么会骗人

我那条流水线的问题，出在检查只走到了「代码能编译」这一层。推代码的认证过期，属于另一层，没人给它写检查。

Anthropic 的做法是给每次提交盖一个章，写明它是怎么验的，包括「没验」。这个「没验」的选项很关键。它让没验过的提交可以被查出来，而不是混在一堆绿勾里。

他们还设了一道提交闸门，三档：关、只看不拦、真拦。先开只看不拦，让它记录下本来会被拦的提交，人看一阵误报，再切到真拦。顺序反了，第一天就会被误报卡住，然后就有人去把闸拆了。同一个会话里被拦两次，第三次会直接放行，免得它卡在那儿动不了。

验收标准不能自己改

文章里有一句我划了线的话。如果一个改动能修改评判它的那道检查，那这道检查就是坏的。

他们的评审规则文件只从主干读，从不读 PR 里的那一份。写代码的 agent 改不到判它的标准。

这一条比「多写几个检查」难得多。我们搭 agent 流水线，最容易顺手把规则、测试、评分标准都放在同一个仓库、同一个分支里。agent 有写权限，就能一起改。它不一定会故意改，但它会在「让测试过」和「把测试松一点」之间选更省力的那个。你给它这个选项，就是给自己埋雷。

检查由谁写，也有讲究。文章说要由代码的主人写，一直改到「它标出来的正是主人会标的东西」为止。只有写这块代码的人，知道哪种错最贵。

三道检查怎么选

他们推荐三种。

端到端最难骗。把真实用户流程跑一遍，加购、结账、确认，功能要么能用要么不能用。属性测试是反过来，先写一句你认为不可能被打破的规则，比如编码再解码要还原，再让工具生成上千个输入去试着打破它。差分测试用于大迁移，新旧两套系统喂同样的输入，结果不一样就是有问题。

如果只能选一种，选端到端。文章说，单元测试更快、更稳，可它能在功能整体坏掉的时候照样通过。写测试的和写代码的，可能都没读懂整个任务。

这一句挺扎心。我自己那条流水线，检查大多停在「文件生成了、格式对了」，离「读者读得下去」还差好几层。你要是有类似的一条线，可以翻一眼它的检查停在哪儿。

如果让我选，我会先上端到端。另外两种等到真出事再补，不提前把检查表堆满。

三轮不过就停工

十月那篇讲评审的文章里，有个数字我看了两遍。一个命令行工具的合并请求（PR），一夜之间跑了五十多轮评审和修复，作者才把它叫停。

他们逐行去追评审反复标出的问题，发现差不多 59% 是评审第一轮就已经在那儿的旧代码。每一轮多翻出来的是几个旧 bug，新 bug 并没有多多少。这样的循环不会收敛。

于是有了三轮上限。三轮还不过，评审就请作者退一步，重新想方案。之后只审新改动，同一个问题不重复提。改完之后，一轮就通过的内部 PR 从 65% 涨到 78%，需要五轮以上的从 8.9% 掉到 1.5%，平均轮数从 2.08 降到 1.32。

他们只写了一行，我觉得最值钱的一句，是这句。噪音对 agent 作者更贵。一个人看到一条无关紧要的意见，几秒钟就挥掉了。agent 不会挥，它会去改，改完就是一个新提交，再来一轮评审。同一套流程，作者从人换成 agent，成本结构就变了。你如果拿给人用的评审流程直接套 agent，最后失控的会是轮数，质量未必跟着涨。

规则自己也要被审

那 39 项可靠性清单，每一项都挂着三样东西：一个能从一次改动里看出来的触发条件、一个检查、以及它背后的故障或 PR。Claude 每次只查触发条件命中的那几项，通常是 3 到 10 项。清单的作用，是让事故在相似改动出现时自己跳出来，不用人背下所有事故。

更值得抄的是规则怎么进出。一条新规则要至少在两个 PR 里出现过，要三个 agent 试着反驳它，还要有人在 PR 里批准。遇到不稳定的测试，跳过、加 sleep、重试到通过这三条路都被堵死。找不到根因，就删掉，并写清为什么删。清单还要定期修剪。一套只进不出的检查表，最后会变成所有人都绕开的那段噪音。

他们还拿过去出过事故的 PR 做了一套考卷，每天让评审者跑一遍。改提示词、改工具、改模型，都要在整套考卷上重新打分，只有分数变好才留下。这条解决的是「谁来评评审者」。答案不玄，就是拿真实事故当标准答案。

我那套流水线的缺口

说回我自己。我那套内容流水线的评阅环节，默认只跑一轮，分数低于 80 也照样往下走。这个设计是我自己定的，理由是流水线要顺，不能被一个分数卡死。今天对着 Anthropic 这套看，我得承认它解决的是「顺」，没解决「可信」。

我手里其实有更硬的东西。我写过 exit 2 的钩子，知道退出码 1 拦不住 Claude，只有 2 才是真拦。可那条钩子管的是「停下来重做」，不管「做完了怎么证明它做对了」。我也没给自己的规则定过进出条件，规则库越写越厚，加一条只需要我觉得有道理。

这篇文章给我的三件事，我打算照做。一件是把评分的标准挪到一个 agent 改不到的地方，至少别让它一边写稿一边改评分规则。一件是给检查加一个「没验」的明确状态，别让没跑过的稿子混在绿勾里。还有一件是给循环定一个轮数上限，到点就停，交给人看。三件都不大，但都是我眼下缺的那半句。

人只剩五件事

那人的位置呢。文章列了五件事：决定要不要做、看高风险代码、看会被别人抄的架构、读证据、为结果负责。

读证据这一条写得具体。测试输出、跑过什么命令、返回了什么、截图、评审意见。你要是说不出这些检查会漏掉什么，就该要一次真评审，别点个通过就完事。

我特别喜欢他们那句运营准则：你合的你负责。谁指挥 agent 写的，谁就是 PR 上必须出现的那个评审人。agent 的批准永远不算人的批准。这跟信不信任模型没关系，重点是责任要落在一个能被追问的人身上。

回到那盏绿灯

那次之后，我给最后一步单独挂了个告警。可今天看，那也只是让「红了」更早被看见，没解决「红了之后谁来判断该不该继续」。

缺的是有人问一句，这盏灯到底照全了没有。模型写得再多，这一句还得人问。

你手上那条流水线，现在最不敢让 agent 自己改的是哪一样？是测试，是评分规则，还是发布那一步？
