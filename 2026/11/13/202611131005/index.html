换掉黄仁勋，1400 万颗卡还在：真正的变量不在那个 CEO 身上

发表于 2026-11-13 更新于 2026-11-14 分类于 观点 阅读次数： 本文字数： 2.5k 阅读时长 ≈ 2 分钟
黄仁勋辞任英伟达 CEO。对开发者来说，1400 万颗已装机 GPU 和 CUDA 生态比人事更硬，短期真正的变量在出口政策，技术栈该留第二套后端。

Hello，我是飞飞。

周三晚上，英伟达的公告出来了：黄仁勋辞去总裁、CEO 和董事职务，即刻生效。第二天的开盘价掉了 14 个点。

市场用脚投了票。但投票的理由，未必跟技术有关。

你可能也在朋友圈刷到了这条。做开发的人第一反应大概跟我一样：这跟我今晚要跑的活，有关系吗？

先把结论放前面。这事有影响，但影响没你想的那么直接。你真正该看的是那 1400 万颗已经插在机架上的卡，和卡上面那套跑了很多年的 CUDA。CEO 这个位子，反而是最浅的一层。

先把发生的事摆清楚

接任的人也定了：首席财务官 Colette Kress，头衔前面挂着临时两个字。

事情的引子，是一段婚外关系。对方是新加坡云服务商 Megaspeed 的高管 Alice Huang。彭博社的报道说，她曾被美国情报机构指认为疑似中国情报人员的线人。这条指控本身，目前没有被公开证实。

再往前追，做空机构 Culper Research 在今年 5 月 13 日的一份报告里，就点过这层关系异常。The Information 后来的报道说，与黄仁勋有关的采购网络，把价值 75 亿美元的硬件转到了中国买家手里。

这些说法都还停在「据报道」的层面。董事会启动了独立调查，黄仁勋本人承认了关系，但没有承认泄密。我写这篇，不打算替任何一方下结论。

值得留意的是速度。董事会先是公开支持他，几天后启动独立调查，再往后就传出接近决定去留。从公开支持到人走，前后不过两周多。一家这个体量的公司，换掉掌舵三十三年的人，用的是这个节奏。

换人不等于换平台

真正值得琢磨的，是英伟达这家公司到底靠什么站着。

Azeem Azhar 给了两个数：过去五年，英伟达卖出了近 1400 万颗旗舰 AI 芯片，占了这个市场 85%。这两个数比任何一位高管都更能说明问题。

份额高到这个程度，定价权就在它手里。你想找一条完全绕开它的路，能选的方案会少很多，短期内也看不到成规模的替代。

CUDA 的护城河，从来就不在某一个人的脑子里。它是十几年来一层层堆起来的：算子库、编译器、调试工具、无数篇只针对 CUDA 写的教程，还有你团队里那几条调了三个月才跑通的 kernel。

换掉一个 CEO，这些东西一样都不少。

Azhar 还点了一个跟乔布斯当年不一样的地方：苹果在 1985 年赶走乔布斯时，公司已经有一套能转的班子。这次没有。接手的 Kress 是 CFO，属于临时过渡。

这会影响一家公司的执行力，会影响它跟云厂商谈的那一堆财务担保，会影响它在欧洲一年近百亿美元的投资节奏。但它不会让已经写好的 kernel 突然跑不动。

护城河长在装机量上

先交代一句：我没有自己买过卡，也没写过 CUDA kernel。所以我说的体感，是站在使用者这一侧的。我每天用的模型，跑在谁的机房里、插的什么卡，我其实不知道。

但我知道一件事：选工具的时候，更值钱的分量是它已经被多少人用过，背后站着谁反而排在后面。

1400 万颗卡的存量就是这个意思。摊到五年，一年两百八十万颗上下。它意味着全世界绝大多数训练脚本、推理框架、报错帖，都是围着这套东西长出来的。

你天天用的 PyTorch，默认后端是它。你调推理时的量化算子，很多只对它做了优化。你搜到的那些答案，也是按它的显存模型写的。你想换的其实是一整段积累：过去几年踩过的坑、调过的参数、记住的报错。

一个很土但很准的测法：去招聘网站搜一下，会写 CUDA 的人有多少，会写 ROCm 的人有多少。这两个数字的差距，就是你团队换栈时要付的学费。

这就是平台和个人的区别。个人会走，平台会留在原地，因为它已经被太多人的工作流焊死了。

真正会变的是政策

那什么会变？我认为是政策。

SemiAnalysis 在辞职后发了一篇长文，把这件事和 RASA 法案、和针对中国远程访问 GPU 的管制联系起来。这是一家分析机构的判断，还没有坐实，我看的时候留了一半。

但方向不难理解。民主党议员已经在 11 月 12 日启动了对英伟达对华芯片销售的调查。牵头的是众议员 Richard Neal 和参议员 Ron Wyden，两人致函商务部长 Howard Lutnick，要求把相关记录先保存下来。

这些动作的开关，不在 CEO 手里，也不在你我手里。

法案这类东西，落点往往在最后一步：谁能远程用到这些卡。卡从哪个港口出去，只是前面一环。云上的算力，一样在射程里。

对开发者来说，这种不确定性比人事变动更实在。它落到你身上的样子，可能是某个区域的 API 突然不可用，可能是云上 GPU 的报价一个月变两次，也可能是你买得到卡、却买不到配套的软件许可。

我的技术栈押在哪

说点具体的。

我每天写代码，靠的是几个模型 API。我不持有算力，也不控制机房。这个事实在平时感觉不到，出了事才会冒出来：原来我整套生产力，是租来的。

大部分开发者跟我一样，并不直接买卡。我们是通过云、通过 API 间接依赖英伟达的。所以这条新闻看着远，传导到身上其实只有一两层。

这算不上悲观，就是一笔账要算清楚。你租来的东西，房东换人了，租金可能变，房子还在。你真正该担心的，是这栋楼要不要拆、什么时候拆。

英伟达这栋楼暂时不会拆。1400 万颗卡在那儿摆着，CUDA 还在迭代，客户的迁移成本还在。

该做的准备其实很朴素

我不打算因为一条人事新闻就去改技术选型。那是最容易被情绪带着走的动作。

但有几件事，平时就该做。

推理这一层留个抽象。别把某一家云的 SDK 直接写进业务代码里，多一层适配，换供应商的时候少掉一层皮。

关键业务准备第二套后端。不一定要现在切，但要知道切过去要多久、贵多少、哪些能力会丢。拿你手上那三个常用的能力去对一遍，长上下文、工具调用、看图片，另一家能覆盖几个，答案就是你的切换成本。

把只支持 CUDA 的依赖单独列一张单子。整理一次你会发现，真正卡住你的可能只有两三个算子，剩下的都能平移。

看新闻的时候，把人和平台分开算。人走了可能带走判断力，平台走了才带走你的产能。

我押得最重的那一块

这类事在工程里不新鲜。某个依赖说停就停，一条产线当天的活就跟着停了。麻烦的地方在于，平时没人会去算这笔账。

我能给的建议很土：凡是离了就不能干活的东西，至少要能说清楚替代方案在哪、切过去要多久。

这次换的是英伟达的 CEO。下次可能是任何一家你依赖的公司。

你现在的技术栈里，有哪一块是真的房东一换就得搬家？评论区聊聊，我想看看大家押得最重的是哪个。
