他有一张表，正好补上我空着的那格

发表于 2026-11-02 更新于 2026-11-03 分类于 观点 阅读次数： 本文字数： 2.6k 阅读时长 ≈ 2 分钟
卡兹克公开的 Agent 自动化系统与作者的写作流水线都收敛到「人只拍板」，但起点不同；他用浏览器每周问六家 AI 的 GEO 做法，补上了作者 6615 次抓取也测不到的那半张表。

Hello，我是飞飞。

昨天卡兹克发了一篇长文，把他折腾一年的 Agent 自动化系统整个摊开了。我从头读到尾，越读越觉得熟悉，因为那套东西的终点，和我这套撞在了一起。

但起点完全不一样。

如果你也在搭自己的 AI 工作流，这中间的差别值得看一眼，它决定你该不该照着抄。

他从事件开始

他开头引了 DeepSeek 一篇架构文章里的话：一个人通常只能同时跟进 3 到 5 个活跃的会话，单任务的上限取决于模型能力，多任务的上限取决于人的注意力。

他的判断是，人就是那个瓶颈。所以要把任务的起点从人身上拿掉，让事件来叫醒 Agent。

他的做法是自建一层「自动化中台」。所有事件先汇到那儿，统一格式，再查一份 rules.json，决定这件事该叫醒哪个 Agent、用哪个模型、开多深的推理。他举了自己的一条规则：同事提了新意见，就在指定代码目录里，用指定的 skill 去处理，最多并行三条，只有拿不准的时候才告诉他。

底下跑活的是一台本地 Mac mini，按任务类型分模型。再往下是一套自建的 CI，五个环节跑完才算上线。

推到他面前的只有一道：飞书里弹一张卡片，他点一下。

他还举了三个自己在跑的定时任务，看那段我才明白「事件驱动」具体长什么样：每天下午，Codex 去微信群、X、小红书、抖音搜大家对他那个产品 AIHOT 的讨论，汇总成一份报告；他们的项目开源在 GitHub，Claude 每天晚上六点扫一遍新提的 issue 和 PR；还有每周那个 GEO 检查。

这些活全都不需要他开口。

统一事件格式这件事，他解释得挺实在：每接一种来源就单独写一套脚本，三五个还行，做到十几个几十个，一定乱成一锅粥。他自己就吃过这个亏，才建了中间那层。

他给那个点卡片的动作起了个名字，叫批奏折。

中间还引了朱元璋：废了丞相之后，八天收到 1660 件奏札，里面三千多件事，一天两百多份，全压在一个人身上。

这个画面他用得准。我不重讲，只留一个数在这里。

闸卡的位置不同

我这套的终点跟他一样：人只做那一道判断。

但两边的闸，卡的不是同一个东西。

他卡的是决策。删数据、花钱、改方向，这三类才推给他，其余全放给底下。

我卡的是动作。改完文件必须跑类型检查，报错就拦住，让 agent 修好才准往下走。格式化和危险命令，也在这一层拦。

这个差别不小。他的放权比我彻底一档：他只在「要不要干」上出现，我在「干得对不对」上还要出现。

我那套是七个阶段必跑，第八个可选：先搜资料，再写稿，接着过一遍防 AI 味的润色，接着是六维评阅，没过八十分就打回去定点重改一轮，再往后是写经验回规则库、配封面、出五个平台的版本。第八个是推公众号，只在我说要发的时候才跑。每一步都留了人复核的口子，但口子的类型不一样。

说句公道话，我不敢像他那样放。我那条流水线跑出来的是要署我名字的稿子，口径错一个数字，代价比一次部署失败大。

他有一张我缺的表

真正让我坐直的，是他提到的三个定时任务之一。

他写：每周操控浏览器，去豆包、DeepSeek、千问、元宝、ChatGPT、Gemini 问一遍他们的 GEO 问题，判断自家产品的 GEO 情况。

看到这句我停了一下，因为我也在测 GEO，但测法完全不一样。

顺带说一句，他挑的这六家里，四家是国内的、两家在海外，这个配比挺实在。

我盯的是 nginx 日志：16 种 AI 爬虫抓了多少、从 AI 引擎点回来多少。十月底那一周被 AI 抓了 6,615 次，点回来 0 次。十九周累计十二万八千多次抓取、153 次回流，0.12%。

这套数据能告诉我「谁在抓、抓了多少、有没有真人来」。它的成本几乎为零：日志本来就在写，脚本每周一自己跑一遍，我什么都不用做。

它告诉不了我的是另一件事：AI 在答案里有没有提到我。

这一点我在十月三十号那篇里自己写过：AI 不告诉你它引用了谁，我数得到有人点链接来了，数不到它在答案里提了我、但没人点。

他的做法正好补这一格。主动去问，看答案里有没有自己。一次几个固定问题，六个引擎，一周跑一遍。

成本低得可以忽略，测的却是我这边彻底空着的那半边。

我不打算建那层中台

看到这儿你可能会问，那我要不要也去搭一套？

我的答案是不要。

他那层中台解决的，是「事件多到三五个脚本管不住」的问题。他自己在文里也说了，接三五个还行，做到十几个几十个，一定会乱成一锅粥。

我一天发一到两篇稿，触发源就一个：我自己想写。给他那层中台，等于给一间只有一个员工的办公室配一套排班系统。

他那层的价值，在于把「事件」变成了可以统一调度的东西。我没有事件可调，我只有待办。

还有个更实在的原因：中台的成本不在建，在养。十几个来源的格式会变，接口会挂，规则会过期，得有人一直蹲着修。我没有那个岗位。

我真正想抄的一件事

不过有一件事，我已经想好怎么抄了。

要抄的跟中台无关，也跟 rules.json 无关。是那个每周问一遍的做法。

我打算固定五到八个问题，都是读者真会去问的，比如「飞飞的AI实验室是谁」「飞飞的AI实验室怎么做 GEO 监测」「Claude Code 怎么写 hook」，每周丢给那六家引擎，把答案和有没有提到我记下来。

记的时候不能只记「提到了没有」。得记它在哪一句提的、旁边还提了谁、引的是我哪一篇文章。这三栏记满四周，才知道自己在这六家眼里到底是个什么位置。

这件事难的不是问，是问什么。问题写宽了，答案全是泛泛而谈；写窄了，测到的只是某一篇文章有没有被命中。我打算先用三类试：一类问「是谁」，一类问「怎么做」，一类直接拿某篇文章的标题去问它会不会被引用。

这样做，那张表就补齐了两头：日志告诉我谁在抓，问答告诉我谁在引用。中间那段「抓了但没引用」，才第一次看得见。

不过有件事我得先说清楚。他那套能一直跑，靠的是他有一批稳定的、会自己发生的事；我这套能跑，靠的是我每天都还坐在那儿。哪天真不写了，我这边是立刻停，他那边还能转一阵。他的事件由用户和同事在发生，我的事件是我想写。这是他比我结实的地方。

我在十月那篇里承认过测不到，现在有人把测法摆出来了，不抄没道理。

所以这件事我分成两半看：他那层中台，多数人不必建，那是规模问题；他那个每周去问一遍的做法，多数人该抄，那是盲区问题。规模不是人人有，盲区人人都有。后者更麻烦些，你根本不知道它在那儿。

我们太容易盯着自己那点数据自我安慰，抓取涨了就当曝光涨了，其实答案里压根没你。

轮到你：你有没有给自己搭过类似的观察？是盯数据，还是直接去问？如果两边都没做，你最想知道的是哪一个数？
