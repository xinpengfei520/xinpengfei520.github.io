把24个浏览器动作全删了：browser-use 1.0 为什么改用 Python 代码控制网页？

发表于 2026-11-21 分类于 技术 阅读次数： 本文字数： 3k 阅读时长 ≈ 3 分钟
开源网页智能体顶流 browser-use 迎来 1.0 重构：砍掉近九成历史代码，删光 24 个离散动作工具，用 Python REPL 与原生 CDP 终结往返地狱。

Hello，我是飞飞。

如果你最近也尝试用大模型搭过网页自动化助手，或者写过帮自己抢票、比价、抓取数据的浏览器 Agent，我想先问你一个非常扎心的体验问题：当大模型在网页里跑起来的时候，你在屏幕前看着它的操作，到底捏过多少把冷汗？

在过去一年的主流设计里，让大模型操控浏览器的逻辑听起来极其直观：既然人类是用鼠标点击、用滚轮翻页的，那就给模型也配齐一套对应的动作。

于是框架作者们辛苦给模型包了一大堆工具：点击某个编号的按钮、往输入框填字、页面向下滚动半屏、切换标签页、拖拽元素。

但只要真拿它去跑复杂业务，整套系统就会迅速陷入一种让人抓狂的笨拙感。

你想让它从电商页面里抓取前二十款商品的名字和价格。模型先看一眼整张网页密密麻麻的节点树，调用一次点击展开；等页面刷新，模型再看一遍节点树，调用一次滚动；接着找到第一个商品，再调一次读取。

每一次极其微小的动作，都要在云端模型和本地浏览器之间完整往返一次。抓完这二十行数据，模型在背后通信了几十轮，烧掉几十万个 Token。只要中间网络稍有抖动，或者页面弹出了一个优惠券，整条漫长的链路当场就会卡死崩塌。

就在昨天，GitHub 上最受欢迎的开源网页智能体框架 browser-use，正式发布了 1.0 重构大版本。

让整个开源社区大跌眼镜的是，作者团队既没有增加更多视觉模型，也没有堆砌更多细致的点击工具。相反，他们做了一个极其激进的减法：

直接把项目里近九成的历史胶水代码全删了，把 0.x 时代封装的 24 个浏览器动作工具全部砍掉，转而只给大模型留了一个核心工具：一个持久化的 Python 交互式运行环境。

核心团队用最硬核的工程重构证明了一件事：让大模型一个动作一个动作地模拟人类点鼠标，从一开始可能就走歪了。

24个动作与往返地狱

要看清这次 1.0 重构的威力，得先复盘 0.x 时代的网页 Agent 到底被什么拖垮了。

在旧架构里，浏览器智能体的工作方式本质上是一个沉重的单步轮询循环。

每推进一步，框架都要把整个网页的 DOM 树扒下来，过滤后转成结构化文本，给屏幕上的每个可点击元素标上数字编号。接着，框架把这几万字的页面快照，加上预先定义的 24 个动作工具的 JSON 说明书，一股脑倒进模型的输入框里。

模型在这个漫长的提示词里苦苦搜寻，输出一个标准结构：“我要调用 click(element_index=42)”。本地框架收到指令，通过自动化接口把鼠标移到那个按钮上点一下，等待页面重新加载。加载完成后，再次重复扒下新的网页树，送回模型做下一步决断。

这种机械的设计直接带来了三重致命代价。

其一是昂贵的说明书税。每个工具参数的字段描述与类型定义，都是真金白银的 Token 开销。24 个动作的说明书不管本轮用不用得上，对话每前进一步都要全量读一遍，大部分预算全浪费在反复交租上了。

其二是网络往返地狱。大模型每次只能挑一个原子工具，任何涉及循环的任务都被拉扯成数十次通信。翻页三次抓五条记录，单步循环必须经历十五次全量握手，耗时拉长数倍，任何偶发超时都会让流程付诸东流。

其三是脆弱的容错能力。某个元素点击瞬间被浮窗遮挡，大模型只能收到报错，重新发起请求思考自救。为了伺候好这 24 个离散动作，团队写了数万行胶水代码做状态同步，系统越写越重，可靠性却始终上不去。

代码即动作的降维打击

browser-use 1.0 拿出的解法，简单粗暴得让人拍案叫绝。

他们不再把模型当成手握遥控器按钮的提线木偶，而是把它当成一个真正的程序员。

在 1.0 新架构里，那份长达 24 项的动作工具清单被彻底清理。取而代之的，是一个底层进程守护的 Python 持久交互环境（REPL），配合直接连通浏览器的 Chrome 开发者工具协议（CDP）。

现在的交互变成了一种全新的范式：代码即动作。

大模型面对网页时，不再去选该点哪个按钮，而是直接写出一小段原生的 Python 代码块。在底层工程机制上，这形成了降维打击般的体验提升。

最显著的变化在于本地控制流的彻底释放。

当模型需要抓取列表里的二十条数据时，在 1.0 里只需要写一个极其朴素的 for 循环。循环在本地 Python 进程里以毫秒级速度跑完，根本不需要每读一条数据就跑去云端跟大模型打一声招呼。

过去需要往返二十次的拉扯，在 1.0 里被压缩成了一次生成、本地极速跑通。执行效率提升了十倍，中间的网络脆弱面被缩减到了极致。

更迷人的是变量与状态的原生持久化。

过去数据传递完全依赖上下文拼接，前一步的订单号必须回传对话历史再重新解析。而在持久 Python 环境里，上一行赋值的变量下一个代码块可以直接调取，临时数据直接留在本地内存里，不再耗费下行 Token。

再加上 Python 原生支持的 try...except 异常捕获机制，瞬时抖动、元素短暂找不到的情况，脚本自己加两行异常重试就顺畅抹平了，完全不需要大惊小怪地退回去让模型重新推理一遍。

大模型负责给出策略和写出脚本，本地执行环境负责高效跑完并消化细节，这才是合理的人机分工。

删掉九成代码的工程清醒

在整个 1.0 重构过程中，最让我感到震撼的，是作者团队对待历史包袱的果决态度。

翻看老版本仓库，团队为了维护这 24 个动作写了海量辅助函数与剪枝算法，本质上全是在为一个先天有缺陷的架构打补丁。很多开源项目走到这个阶段时，往往舍不得沉没成本，选择在老架构上继续堆叠补丁，最终在复杂的死锁里把自己耗死。

browser-use 团队在 1.0 里展现出了一种罕见的工程清醒：既然发现了代码即动作的优越性，就坚决砍掉近九成的冗余胶水层，把底座整体切换到成熟的 Pydantic AI 框架上。

借助 Pydantic AI 提供的严密类型安全与生命周期管理，核心执行器变得极其轻量透明。执行脚本的子进程被严格隔离在独立的进程组内，带超时监控与安全过滤，跑飞了直接精准熔断重启，既保证了本地环境安全，又把执行延迟压到了极限。

这一刀切下去，不仅仓库从臃肿的巨石系统瘦身成了轻巧的执行引擎，连带着让下游使用者的心智负担也轻了一大截。只要会写基础自动化脚本，就能顺畅调度整个框架。

智能体工具链的终局反思

把 browser-use 1.0 的这次蜕变，放进整个智能体开发生态的坐标系里看，会发现一条极其清晰的技术演进轨迹。

前几天 Google 在 Gemini API 里上线 Tool Retrieval，大家都在感叹，智能体不能再把几十个工具说明书死死塞进输入框了。

而 browser-use 1.0 则用更决绝的方式给出了另一种答案：如果一个工具的通用性足够强，你甚至根本不需要准备几十个工具。

过去一年里，几乎所有 Agent 框架都在跟风做加法。大家把各个平台的 API 包装成看似规范的 MCP 工具，越塞越满，误以为工具越多能力边界就越宽。

但生产实践正在击碎这套逻辑。工具越多，模型的选择成本越高，出错概率呈指数级上升。

最好的通用工具，往往是一整套能按需组装、具备完整逻辑控制能力的通用机床。

让大模型直接写代码去驱动现实系统，而不是靠人工设计的 JSON 工具去猜意图，正在成为下一代高阶智能体的共识底色。从这个角度来看，browser-use 1.0 删掉的那 24 个动作，反而是这个赛道走向成熟时极其重要的一次成人礼。

如果你平时也在折腾智能体调用或者浏览器自动化，不妨也回过头审视一下自己的工具箱：你现在塞给大模型的那一堆细分动作里，到底有多少是在给它添乱？把这些脏活换成一段直截了当的代码，你的系统又能轻快多少？欢迎在评论区聊聊你的重构心得。
