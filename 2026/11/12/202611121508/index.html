你以为 agent 在干活，其实它在烧钱

发表于 2026-11-12 分类于 AI 阅读次数： 本文字数： 2.8k 阅读时长 ≈ 3 分钟
AI agent 卡进无限循环时成本越滚越高，每次重试都带全量上下文。OpenRouter 实测只加 doom-loop 检测，调用就从 314 次降到 64 次、费用降 83%；另三层防护补上换参数、换策略和代码出 bug 的盲区。

Hello，我是飞飞。

先问你一句：你手上那个跑在后台的 agent，万一卡住了，谁会知道？

之前我设想过一件事，把编程 agent 的 SDK 接进写作流水线，让它夜里自己跑。入口想好了，工具也想好了，只有一样没算清楚，它要是卡在某个报错的步骤上，一晚上能烧掉多少额度。想到这儿，我没敢直接上。

这不是我多虑。AWS 上有过一个文档处理 agent，收到一个畸形的接口返回，几小时里调了几千次，账单最后是一万美元。用户把浏览器关了，后台的 agent 还在跑。

agent 卡住的时候，不会喊一声「我卡住了」。它只会一直重试同一个失败的步骤，每次重试都把前面的失败记录一起带进上下文，越跑越贵。

所以问题不在它会不会出错，在出错之后，有没有东西替它踩一脚刹车。

为什么会卡进无限循环

agent 的运行逻辑是这样的，模型不断调工具，工具返回结果，模型根据结果决定下一步，直到它认为任务完成为止。

工具一失败，agent 不会停，它会把这次失败当成一道待解的谜题。

这和普通程序完全不一样。你写的代码，数据库查询失败就会抛异常、流程终止。但 agent 拿到失败结果，它的反应是，工具报错了，那我再想想，换个办法试试。

所以它就一直试。

每次重试都要把之前所有的对话历史一起打包发给模型。上下文不断膨胀。OpenRouter 做过一组测试，记录了一个 agent 在无限循环里的开销，第一轮进去 131 个 token（模型按 token 计费），到后面某一轮已经是 3,262 个 token。同一条对话，越往后越贵。

加速烧钱，不是匀速。

一次测试说明了什么

OpenRouter 最近发了一篇文章，记录了他们的测试过程。

他们造了一个场景，一个账单 agent，负责调接口查发票金额。接口设计成永远超时，模拟「服务挂了但没人修」的情况。

他们拿了六个模型来跑，不加任何防护，只设了一个 40 步的硬上限。18 次测试里，有 4 次直接撞到上限。Mistral Large 4 三次分别发起了 11 次、41 次、41 次工具调用；Grok 4.7 是 41 次、12 次、41 次。同一个输入，同一个模型，这一轮 12 次就停了，下一轮能一头撞到 41 次。41 次而不是 40 次，是因为还有一次没返回的调用也被执行了。

循环不是每次都发作，它像抽风。一次干净测试，说明不了生产里不会卡。

他们统计了全部 18 次测试（六个模型各跑三次），一共产生了 314 次工具调用，花了 $0.29。

只加一层 doom-loop 检测，同样的测试就变成 64 次工具调用，$0.05。

调用次数降了 80%，花费降了 83%。

四层防护，各管一段

OpenRouter 的 @openrouter/agent SDK 给出了四层方案。每一层针对不同的失控模式，缺任何一层都会有漏洞。

第一层，doom-loop 检测

原理很简单，给每次工具调用做指纹（工具名 + 参数），发现连续几次指纹完全相同，就认定进入了无意义重复，主动介入。

默认的行为是，第 2 次重复时记一个观察标记，第 3 次时阻断这次调用，告诉模型「你在重复，这样做不会有不同的结果，请换个思路」，到第 6 次时直接终止整个任务。

这个「告诉模型」很关键。不只是报错，而是给它一个明确的信号，你陷入循环了，这条路走不通，停下来。大多数模型收到这个信息后会立刻切换策略，给出一个最终答案结束任务。

没有这个信号，它会一直尝试下去，每次都把完整的失败历史重新发出去，越来越贵。

OpenRouter 测下来，加了 doom-loop 检测之后，18 次测试里有 16 次在两次真实工具调用后就结束了。大多数情况这一层就能拦住。跑长任务，这一层应该最先加上。

第二层，参数归一化

有些模型收到阻断信息后，会换一个接近的参数继续试。发票号从 INV-2291 换成 inv-2291，或者去掉横杠变成 INV2291，换了大小写，指纹就是新的，doom-loop 检测就重置了。等于打一下换个马甲，绕过了检测。

Mistral Large 在 9 次测试里有 5 次用了这个方法，GPT-6 Luna 也有类似行为。

loopKey 解决这个问题。你告诉检测器，这个工具判断是否是同一个调用，只看发票号里的数字部分。这样 INV-2291、inv-2291、INV2291 全部映射到同一个指纹，模型变着花样试也逃不掉检测。

第三层，步数 + 成本双上限

前两层处理的都是「同一个工具反复调」的情况。但如果模型每次都换不同的策略、调不同的工具，这两层都没用，指纹永远是新的，它就一直跑下去。

stopWhen 解决这个问题，设一个最多跑多少步，再设一个最多花多少钱，哪条先到就停哪条。

成本上限比步数上限更重要。 因为 agent 循环的开销不是均匀的，越到后面上下文越大，单次调用越贵。只设步数上限，后 15 步很可能比前 15 步还贵，步数没超，成本已经超出你的预期了。

这两个数怎么定，放到最后一节一起说。

第四层，API key 信用额度

前三层都跑在你的代码里。如果代码有 bug 漏掉了这三层，或者你忘了部署最新版本，该失控还是会失控。

最后一层是在路由侧（比如 OpenRouter）设一个 key 级别的信用额度上限。可以给每个 agent 或者每个用户单独配一个 key，单独设上限。这个限制在服务端执行，不经过你的代码，哪怕你的 agent 代码出了问题，也拦得住。

超出上限会返回 402，错误响应里带一个 limit_source 字段，你可以据此决定是提额度还是当作停止信号处理。这一层替代不了前三层。它只负责兜底，万一前三层都失效了，这里还有一道闸。

这四层叠在一起，才是完整的防护。某一层单独用都有盲区，合起来才能覆盖大多数失控的情况。

今天就能装上的刹车

一个 agent 上线之前，值得先回答清楚三件事。

先问有没有人盯。 这道闸就是，有没有人会看着它跑。自动化任务最危险的，会出错还是小事，出错了没人知道才最要命。刚才那个 AWS 的案例，最阴的一层就是用户关了浏览器，后台还在跑。如果 agent 是在后台无人监督地跑，就要给失败配一个告警，哪怕只是发一条消息到手机，让你知道它停了、为什么停。这件事做起来不麻烦，但大多数人在自动化跑起来之前都觉得「应该没问题的」，过后就不做了。这一条最容易被跳过。

我看到过一句话，说得很准：你的循环要是没有这个检查环节，那它就不是循环，是一台很自信的烧钱机器。

再算钱。 这个 agent 跑一次大概花多少。不要靠感觉，手动盯几轮，看清楚实际的调用次数和费用，再设上限。上限要比你测出来的正常值高一倍左右，留出余量，但不要设成一个无限大的数字。

接着想失败。 哪些工具可能会失败，失败了该怎么办。如果工具失败的概率不低，就不能指望 agent 自己处理好，需要在工具层面明确告诉它，这个接口挂了，请告诉用户，不要继续重试。这个提示要写进工具的错误返回里，不是系统提示，系统提示 agent 不一定会照做。

agent 的价值，是把你从重复劳动里捞出来，让你去干更值钱的事。可它替你干活的前提，是它该停的时候能停。

给 agent 设上限，其实是给自己画一条安全线。线画了，你才敢让它夜里跑。

你现在跑着的 agent，给它设上限了吗？
