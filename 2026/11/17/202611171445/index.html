2G 内存小机器卡死：一次服务器事故排查的四个反转

发表于 2026-11-17 更新于 2026-11-19 分类于 技术 阅读次数： 本文字数： 2.6k 阅读时长 ≈ 2 分钟
一台 2C2G 阿里云服务器突发假死，排查揭开四大反转：无 OOM 记录但 I/O 达 93%、Redis 因无自启丢失、回滚容器抢占 1001 端口、Nginx 静态解析致 502。本文记录完整排障与动态 DNS 改造。

昨天早上刚坐到电脑前，打算登录服务器看一眼日志，结果敲完 SSH 连接命令，终端的光标就像断了网一样僵在屏幕上。

按回车没有回显，按 Ctrl+C 毫无反应。好不容易艰难挤进终端，敲一行简单的查看命令都要等上三五秒。

我这台跑在阿里云上的 ECS，配置是一台极其典型的小机器：2 核 vCPU、1756MB 内存（大约 2G），外加 3G 的 swap 分区。上面塞着我的个人博客、MySQL 数据库、图书服务、内容工厂以及 Nginx。

起初我以为又是一场平平无奇的内存打满被 OOM 杀进程的惨剧。但当我花了大半天时间，把系统内核日志、Docker 状态机、GitHub Actions 流水线和 Nginx 的解析机制一层层扒开时，却接连撞上了四个完全击碎固有常识的反转。

别再盯着 free 瞎焦虑

很多运维或后端新手看内存，下意识敲出 free -m，盯着 free 那一栏看。

当看到 free 只剩下 69MB 甚至几十兆时，心里立刻咯噔一下，认定内存已经濒临爆炸。

我刚登上去时也是这个感觉。但只要你稍微熟悉 Linux 的内存管理哲学，就会明白 free 极其容易骗人。

Linux 操作系统为了追求极致的文件读写效率，只要系统有多余的空闲内存，就会主动把它们拿去做文件页的缓存。

真正用来衡量一台机器还能不能接纳新进程的，是最后一栏的 available。

在我停掉几个长期不用的容器之后，free 虽然看似只有七八十兆，但 available 其实始终稳健地保留在五百多兆以上，占到总内存的三成左右。

更深层的反转在于：我用命令扫遍了系统内核日志，根本没有找到任何一条 OOM 杀进程的红色记录。

真正把整台机器拖垮拖死的，是各个容器平时没有设置内存上限，过度承诺的内存总量超过了安全限制线，迫使系统不得不把大量匿名页频繁换出到磁盘的 swap 分区里。

随之而来的，是磁盘读写通道被彻底堵死，I/O wait 峰值一路狂飙到 93%，整台机器的负载直接冲到了 30 以上。

它根本不是被内核一刀毙命的，而是被无休止的磁盘换页活活耗到了假死。

Redis 消失的真正元凶

稳住系统负载之后，我顺手检查业务容器，赫然发现核心的 Redis 容器竟然不翼而飞。

我的图书应用依赖它来缓存用户登录态。如果连 Redis 都无声无息地挂了，那肯定是扛不住系统压力倒下了。

然而当我执行命令检查旧容器的退出状态时，跳出来的数字让我愣在原地：

容器的退出码是清清爽爽的 0。

这意味着什么？这意味着它是正常关闭的，压根没有发生任何程序崩溃，更没有遭遇内核强制处决。

翻开它的退出日志，真相更加令人啼笑皆非：日志清清楚楚地记录着，Redis 收到了一条标准的终端退出信号。它慢条斯理地完成了 AOF 文件的同步刷盘，做好了最后一次 RDB 快照保存，然后留下一句体面的告别语，安全退出了。

它之所以在系统重启后彻底失联，根本原因在于它的重启策略被写成了 restart=no。

前一晚我在控制台强行重启服务器时，Docker 守护进程优雅关闭了所有容器。而在服务器重新开机后，因为没有任何机制负责去重新唤醒它，它就一直安安静静地躺在停止列表里。

它压根没有在压力面前崩溃；只是被正常关机之后，再也没人去叫它起床。

回滚容器抢走宿主端口

既然机器清理出了内存，我顺手在博客仓库里提交了新改动，心想着通过 GitHub Actions 的自动化流水线把新文章部署上线。

几分钟后刷新网站，页面毫无变化。打开 GitHub Actions 一看，构建明明打着漂亮的绿勾，部署却刺眼地挂着红叉。

排查日志，赫然看到一行报错，提示端口 1001 已经被分配。

我的博客采用了一套经典的小机器无缝发布策略：线上容器占用宿主机的 1001 端口；每次部署时，旧容器更名为备份并停止，新镜像启动占用 1001，验证通过后再把备份更名为回滚槽位，安静地保持停止状态作为兜底。

整套自动化脚本的运行，全都建立在一个极其脆弱的假设上：回滚容器必须时刻处于停止状态。

但就在前一天下午排障时，为了临时拉起网站，我曾经在宿主机上手动敲命令把回滚容器给启动了。

回滚容器一旦活着，它就死死咬住了宿主机的 1001 端口。

当自动化流水线兴冲冲地拉取了最新镜像准备启动时，发现宿主端口早已名花有主，Docker 直接抛出 128 异常拒绝启动。

很多人以为只有改动了业务代码才会导致部署失败。但现实是，人工运维在深夜随手留下的一个状态缺口，就能让跑了成百上千次的自动化流水线彻底瘫痪。

给 Nginx 接上动态解析

把回滚容器手动停掉、重新把新版拉起来之后，另一个潜伏已久的隐患浮出了水面。

在 Docker 容器网络里，Nginx 往往充当着所有域名的总入口。之前的配置文件里，反向代理地址直接写着容器名。

这种静态写法在绝大多数时候看似岁月静好，但它有一个致命的死穴：Nginx 只会在服务刚启动或者重载配置的那一瞬间，去解析一次容器名对应的局域网 IP，并将其永久缓存下来。

而在日常的容器化部署中，旧容器销毁、新容器重建，Docker 分配给新容器的内网 IP 经常会发生变动。

这就导致了一幕极其滑稽的场面：新容器明明已经在后台跑得好好的，Nginx 却依旧顽固地朝着那个早就化为乌有的旧 IP 拼命转发流量，用户浏览器里全是一片刺眼的 502 报错。

为了根治这种由 IP 漂移引发的断流，我把 Nginx 的转发逻辑彻底重构成了动态 DNS 解析。

利用 Docker 内置的 DNS 服务地址，在配置里加上动态解析器，把缓存有效期定为 5 秒，并将后端地址抽成变量。

这样一来，即便后续自动化流水线频繁销毁并重建容器，Nginx 也最多只会在 5 秒钟内自动更新到最新 IP。

用区区几秒钟微不足道的缓存窗口，换来了整条发布链路的彻底解耦与无感自愈。

小机器运维的防御边界

折腾完这一整套流程，看着服务器可用内存稳定回到 520MB，磁盘占用从 63% 降到 43%，博客和各项服务全部满血复活，我长长舒了一口气。

对于很多习惯了动辄几十核、上百 G 内存的高配服务器的开发者来说，在 2G 内存的小机器上扣成本，听起来或许有些局促。

但这种极端有限的资源环境，恰恰是一面照出所有工程漏洞的明镜。

真正决定系统稳定性的，很少是服务器堆砌了多么庞大的硬件规格；更多是我们在每一个接口、每一个端口、每一个生命周期里，划下的防御边界到底有多硬。

学会把不再使用的僵尸容器连根清理，学会给长期跑在后台的服务设死内存上限，学会把自动化脚本的每一步假设都加上锁和预检。

当你在小机器上把这些繁复的状态机逻辑全部捋顺，再复杂的生产架构，在你眼里也不过是由这一个个扎实的防御零件拼装而成的透明城堡。
