20 亿次请求仅 60 次错误：Anthropic 怎么用 AI 把系统砸碎再修好的

发表于 2026-11-18 更新于 2026-11-21 分类于 技术 阅读次数： 本文字数： 2.8k 阅读时长 ≈ 3 分钟
上线前两周，Anthropic 用 Claude Code 并发调度 30 个智能体全天候狂轰系统，在 20 亿次请求中仅出现 60 次服务器错误。深度拆解官方这套零回滚的混沌测试闭环。

很多每天在终端里使唤 Claude Code 的工程师，日常最习惯的用法，无非是遇到报错随手甩一段日志，或者让它手搓一个组件。

大家普遍把智能体当成手脚麻利的初级程序员：我指哪，它打哪，代码写完我顺手合入主干。

但就在昨天，Anthropic 官方技术博客发了一篇长文复盘，把整个工程圈子看得瞠目结舌。

写文章的工程师 Vivek Nair，负责的是九月中旬正式发布的协作编辑器 Claude Docs。

在官方战报里，最扎眼的是一组颠覆常识的稳定性数据：上线首周生成了 460 万篇文档，承受了超过 20 亿次请求，整个服务在九月累计完成 629 次生产发布，而全链路产生的服务器 500 错误，仅仅只有 60 次，版本回滚次数更是直接挂零。

很多架构师的第一反应，大概都会觉得背后有一支庞大的顶尖运维团队在通宵轮流看守。

然而现实恰恰相反：在正式上线前两周，这项服务还只是跑在单机上的原型玩具；真正帮他们接住 20 亿次请求的，是一个被放出去全天候故意搞破坏的智能体集群。

单机到海量的两周绝杀

把时间倒拨到九月初，Claude Docs 面临的处境可以说是典型的工程噩梦。

这项功能此前在内部小规模跑了几个星期，几千名员工在单台机器上修修补补，跑得挺欢。

但内部玩具和公网上线完全是两个世界。

按照当时测算，一旦面向全球开放，前几天就会涌入数百万量级的文档创建需求。

在传统工程体系里，把单机原型重构成能抗住高并发的分布式后端，哪怕抽调骨干小队，少说也得折腾五六个月。

但摆在工程师面前的倒计时，只剩下两周。

如果按部就班写压测脚本，人工能覆盖的边界少得可怜。人的思维天然带着盲区，写用例时总会默认网络连接稳定、内存回收正常。

但真实的生产环境是一座永远充斥着意外的泥潭。

于是他们做出了极其大胆的决定：既然人脑算不尽所有死法，那就把刚发布的新版大模型放出来，让它去预演成百上千种最偏执的灾难现场。

派三十个智能体去砸系统

九月四号那天，工程师在内网拉起了一套与生产完全镜像的预发集群，开启了一场长达两周的混沌循环。

调度中枢是一个常驻运行的 Claude Code 协调会话。

它自己不编写业务代码，而是在后台像工头一样，并发管理着峰值多达三十个子智能体。

演练场景苛刻得有些神经质：单日塞进千万篇新文档；两万两千个连接在一秒内同时断开又重连；在数百人在线编辑超长文档时，突然拔掉节点电源，顺带人为制造数据库假死卡顿。

每一轮演练的逻辑极其咬合。

压测套件把系统接口推向过载饱和；随后智能体通过遥测接口抓取底层指标。它能直接看到每条 SQL 扫描了几万行数据、吐出几行，内存是以每秒多少兆的速度在飙升。

看到指标异常后，智能体自己给出诊断与优化建议。协调员甚至连接了内部沟通通道，主动向其他负责过类似大规模基础设施的资深智能体请教，提前把别人踩穿的地雷全部记在账上。

改代码前先看可不可逆

看到这里，很多运维同学心里大概会猛地抽搐一下：让几十个智能体在预发环境一边高压施压、一边改代码上线，真不会把集群改上西天吗？

Anthropic 能把危险动作变成生产级常态的关键，在于极其清醒的硬防线：以改动的可逆性为界划分权限。

测试循环里的所有动作被明确切成两半。

一类是低风险的可逆操作。改写低效 SQL、加一层本地缓存、微调并发限流参数。这类修改即使改砸，只要回滚补丁或拨回开关，系统瞬间复原。智能体拥有最高行动权：改代码、部署预发、重新施压验证，人类全流程不用多看一眼。

另一类是高风险的不可逆改动。修改底层表结构、重构键值命名、调整快照落盘的持久化逻辑。

这类修改牵一发而动全身，一旦在老数据上执行迁移，就没有后悔药可吃。

只要撞上这类操作，智能体会立刻踩死刹车，打印前因后果与备选方案，等待工程师手动确认。

这种用法根本不是拿大模型当代写代码的替身，而是让它成为测试基础设施极限的试金石。人把控底层架构命门，机器在沙盒里穷尽所有微观排列。

为了让算法读懂而选型

复盘长文里最值得深思的细节，是他们为了让 AI 顺畅协作，反过来重构了技术选型。

以往选语言框架，考量的是语法顺手、招人方便、生态轮子多。

但在 Docs 底层架构里，主导选型的核心标准，变成了系统对算法的透明可读性。

为了让大模型在排查故障时看清细微脉动，工程师果断放弃带有垃圾回收机制的语言，底层全面拥抱 Rust，对引入第三方库极其克制。

背后的逻辑残酷而现实：如果运行时在底层偷偷搞垃圾回收，内存何时上涨、CPU 为何偶尔卡顿几百毫秒，连人类都解释不清，智能体更不可能精准推导出根因。

系统里的每兆内存、每个算力尖峰，必须能原汁原味回溯到团队写的代码里。

测试初期，曾有一篇超大文档把单个容器内存吃到了三吉字节。

智能体最初也尝试缩小本地缓存。但下一次压测跑完，监控立刻揭穿真相：内存在别处依然暴涨，真正吞噬资源的，是一个第三方依赖内部偷偷维护的隐藏缓存表。

指标足够透明，智能体果断丢弃无效修改，重写了底层调用。

当智能体发现指标无法解释异常时，它甚至会自己跳进源码，在关键路线上手动补上打点探针，再跑一遍，直到把真相逼出来。

十二万刀省下半年工期

文章末尾，作者十分坦诚地把项目的开销账本亮了出来。

从八月底搭建环境到九月中旬上线，两周多的高强度演练，累计消耗了价值十二万五千美元的推理额度。

单看十二万美元，对于刚起步的团队确实不算小钱。

但放进大型服务发布的坐标系里，这笔账划算到了极点。

一个抗住二十亿次请求、六百多次发布零回滚的系统，过去需要三四名资深架构师耗费半年工时，还得在上线当晚通宵盯防。

十二万美元算力，把半年的风险排查硬生生压缩到了两周之内。

更关键的是作者为普通团队做的换算。

Anthropic 烧掉十二万，很大程度是面对全球级编辑器的超高并发，且消耗了大量摸索流程本身的试验算力。

对于日常跑在两三个节点、挂着普通数据库的中小业务而言，类似的压测根本不需要庞大阵仗。

按作者测算的极简方案，单个工程师带上 Claude Code，结合现成监控接口跑一套小规模混沌循环，预计只需三千到一万美元额度，就能把新系统彻底洗礼一遍。

这不再是大厂特权，它正在变成每个认真做产品的团队都能触碰的工程武器。

让破坏者成为护城河

看着官方这份战报，我忍不住反思很多团队日常调教大模型时的保守姿态。

过去这一年，太多人争论 AI 会不会抢走饭碗。很多团队小心翼翼把智能体圈在单测与补全的角落里，生怕它搞乱规矩。

但 Claude Docs 的大捷揭示了截然相反的现实：

智能体真正的上限，在于拥有永不疲倦的破坏欲和对海量故障排列组合的推演速度，而不仅是模仿人类敲出温顺的代码。

它可以在人类进入梦乡的深夜，把架构扔进几万种极端恶劣环境里摩擦；它可以在几小时内把未来几个月可能暴雷的冷门死锁，提前在沙盒里诱导出来。

我们不需要一个小心翼翼、生怕犯错的初级学徒。

我们需要的是一个在上线前敢于把系统砸得粉碎、在天亮前又把它修补得固若金汤的数字先锋。

当越来越多的人还在把 AI 当成打字机的时候，真正老练的团队，早已把这个不知疲倦的破坏者，焊成了自己架构上最坚不可摧的护城河。
