少点一次回车，代价是 2539 个生产密钥裸奔

发表于 2026-11-10 更新于 2026-11-12 分类于 编程 阅读次数： 本文字数： 3.3k 阅读时长 ≈ 3 分钟
Claude Code 因记录自动批准命令，导致 10 万份本地配置上 Git，泄露 2539 个生产密钥。单凭全局忽略防不住跨设备提交，开发者须在项目级忽略文件中明确排除并排查提交历史。

Hello，我是飞飞。

你在终端里用 Claude Code 写代码的时候，大概率遇到过这样的提示：它准备执行一条数据库查询，或者用 curl 调一个带鉴权头的接口，终端停下来等你的回车授权。嫌每次确认麻烦，很多人顺手就按下了那个选项：「允许，并且不再询问」。

那一瞬间你可能觉得自己赚到了。工作流变丝滑了。但我得给你提个醒，先把手头的活停一停。应用安全公司 Apiiro 联合 Ars Technica 刚披露了一起严重的凭据泄露事件：就是这个为了省事的自动批准动作，已经把两千多个真实的生产环境密钥，白纸黑字送上了 GitHub 公开仓库。

这不是黑客利用了零日漏洞，也不是有人攻破了 Anthropic 的服务器。它是每一个追求效率的工程师，在最日常的操作里亲手埋下的雷。

2539 个密码裸奔

先看 Apiiro 这次拉出来的真实数据。

安全研究员在 GitHub 上针对 Claude Code 的本地配置文件做了一次全网扫描。他们在公开仓库里找到了超过 10 万份本该留在本地的配置文件。对这些文件进行深度解析后，确认在 1994 个独立代码库里，赫然暴露了 2539 个完全有效的真实凭据。

这 2539 个凭据不是测试环境里的假数据，而是覆盖了 63 个组织的核心生产资产。

其中包括 Azure 生产数据库连接密码、Square 和 Stripe 支付接口令牌、AWS 和 Supabase 管理密钥、npm 发布令牌，甚至还有服务器的 root 级 SSH 私钥。一旦恶意爬虫扫到这些仓库，拿下服务器或清空数据库只需要写个脚本。

事件曝光后，Anthropic 的 Claude Code 团队负责人 Boris Cherny 已经在社区公开回应，承认早期版本的工具在设计时确实没有做凭据脱敏清洗，目前团队正在全力排查并推进内置的安全扫描与修复机制。

但比起官方的亡羊补牢，更值得搞清楚的是：我们天天在用的终端工具，到底是通过什么机制把家底悄悄推到公网上的？

一键放权的暗账

问题的根源，藏在那个极度人性化的自动批准功能里。

当你让 Claude Code 帮你在本地调试服务、跑迁移脚本或请求外部接口时，终端经常需要执行带参数的命令行。比如连接测试库排查数据，命令行里跟着明文密码；或者调用三方 API，命令里拼了带有 Bearer Token 的请求头。

默认情况下敏感命令会等人工放行。但只要你按下了「不再询问」，工具就必须在本地持久化规则，下次直接静默放行。

技术实现本来可以有很多种做法。比如对命令做模式匹配，或者只提取不带敏感参数的可执行程序名。但 Claude Code 的实现方式非常粗暴：它直接把整条命令的完整字面量，原封不动写进了项目根目录下的 .claude/settings.local.json 文件中。

你在命令里敲下的每一个字母、每一串密码、每一个私有 Token，都被完整写进了磁盘上的普通 JSON 文件。

这就像是你雇了一位做事利索的管家。为了让他帮你进书房取文件，你告诉了他保险柜的密码。管家把事情办妥了，但他怕自己下次记不住，顺手拿出一张便利贴，把密码一字不差写在上面，然后贴在了你家防盗门的外侧。

全局忽略的致命盲区

有人可能会好奇：Anthropic 难道没想过防止这个文件被提交进 Git 吗？

他们确实想过，但选择了一种最脆弱的防护方案。Anthropic 在设计 Claude Code 时，尝试把这个本地配置文件注册到操作系统的全局 Git 排除列表中，也就是用户个人目录下的 ~/.config/git/ignore。

从理论上看，只要全局忽略生效，Git 确实会视而不见。但在真实的多人协作和工程开发环境里，依赖全局忽略简直就是给灾难开门。因为全局忽略文件属于开发者个人机器的环境配置，它从来不会跟着项目代码库一起打包流转。

试想这样的高频场景：你在办公室电脑上配好了环境，全局忽略安然无恙；但晚上回到家，你把仓库克隆到了笔记本上排查问题；或者你在测试机、Docker 容器里拉取代码跑验证。在这些全新的环境里，根本没有针对 Claude Code 的全局排除规则。只要你在新环境里跑了一次命令，.claude 目录就会出现在 git status 的未跟踪列表里。

更要命的是，Apiiro 发现 Claude Code 作为一个具备终端执行与 Git 提交权限的智能体，有时甚至会主动在生成的提交中把这个配置文件添加暂存。开发者习惯性敲下一句 git add . 或者放权让智能体直接提交推送，带有生产凭据的文件就这么被推上了 GitHub。

只要你的仓库是公开的，或者将来从私有转成了公开，那些躺在配置里的明文密钥，就已经暴露在全世界的扫描器之下了。

扫描器为什么漏报

很多成熟的技术团队都配置了安全门禁，比如在 CI/CD 里跑 Gitleaks、TruffleHog，或者开启了 GitHub 官方的 Secret Scanning。为什么这次还有两千多个凭据能在公网安稳躺着？

Apiiro 在报告里点出了一个极其讽刺的事实：在他们确认有效的凭据中，有 215 个凭据在主流开源密钥扫描器的默认规则下被彻底漏掉了。传统的密钥扫描器大多针对经典的代码编写场景，擅长识别代码里硬编码的常量声明，比如变量名叫 AWS_SECRET_KEY，后面跟着一串特定正则前缀的字符串。

但在 Claude Code 的场景下，凭据不是孤立的代码常量，而是被包裹在一整条长命令里，再被转义嵌套进 JSON 的数组或对象内部。命令里混杂着管道符、环境变量替换和转义引号。这种层层嵌套的复杂结构，直接把常规扫描器的正则匹配打懵了。

扫描器以为那只是一段普通的工具配置文本，直接放行通过；但对黑客的扫描脚本来说，提取其中的敏感字段并不困难。防线一旦在边缘失效，剩下的全靠警惕性。但在人人都信任 AI 的时代，警惕性恰恰消耗得最快。

三步查清你的项目

面对已经发生的事情，恐慌没有意义。作为每天都在终端里重度使用 AI 辅助编程的开发者，我们现在最该做的是立刻动手排查。

第一步，检查忽略规则。千万别指望全局配置，必须在项目根目录 .gitignore 里把 .claude/ 目录和 *.local.json 写死，切断被跟踪的可能。

第三步，也是最关键的一步：轮换密钥。如果你发现自己的项目确实曾把带有真实凭据的配置文件推送到过远端，请在第一时间登录对应的云平台或服务后台，吊销旧凭证并生成新密钥。在公网安全领域，一旦凭据离开本地，就必须按已被泄露的最坏情况来处理。

给终端智能体立规矩

这次 Claude Code 的凭据泄露，不是孤立的技术瑕疵，而是整个行业在从代码补全迈向终端代理时，必须补上的一堂安全课。

过去几年，我们对 AI 编程安全的防范重心，主要集中在 AI 生成的代码有没有 SQL 注入、有没有越权逻辑。但当智能体开始接管命令行、拥有读写文件和调用外部工具的权力时，风险的重心已经转移到了智能体自身的本地状态管理上。

为了追求极致的用户体验，厂商倾向于帮开发者砍掉确认环节，把交互阻力降到最低。可阻力最小的地方，往往也是防御最空虚的地方。

在日常使用中，最稳妥的做法是坚守最小权限原则。永远不要在直接敲给 AI 的终端命令里硬编码敏感密码。无论是数据库连接串还是 API 密钥，统一通过本地系统的环境变量来注入。哪怕命令本身被工具原文记录下来，文件里留下的也只是一个变量名，而不是赤裸裸的密码字符串。

AI 编程助手正在重塑开发模式。但无论工具多聪明，终端那一头的最终责任人始终是坐在机器前的工程师。
