榜单同为36分，Muse Ember 单项任务成本约低66%

发表于 2026-11-10 更新于 2026-11-12 分类于 AI 阅读次数： 本文字数： 2.8k 阅读时长 ≈ 3 分钟
Muse Ember 与 Haiku 5.5 的总榜整数分同为 36，Artificial Analysis 估算每项任务成本约低 66%；但终端和真实工程编码表现不同，选型得看具体任务。

Hello，我是飞飞。

你给 Agent 挑模型，会先看总分，再看每百万 token 多少钱吗？

Meta 新出的 Muse Ember，刚好把两把尺子搅到了一起。Artificial Analysis 页面把它和 Haiku 5.5 都显示为 36 分。按 Meta 列出的一位小数，Ember 是 35.8，Haiku 是 36.2，四舍五入后才并列。

AA 算出的单项任务成本约为 Haiku 的三分之一，也就是低约 66%。

可你要是据此把“代码活都换它”，可能就选错了。

Meta 在官方介绍里，把 Ember 定位成一个高频干活的小模型。它面向工具调用和编码子任务。也做路由、信息提取与文档处理。名字里带着 coding，容易让人以为它是便宜版编程模型。第三方评测给出的结果更细。它在一些 Agent 和终端任务上跑得不错。真实工程改动的成绩，却落后于 Haiku 5.5。

这篇不打算把它吹成万能 worker。我想把两个问题拆开：同分为什么成本差这么多？它适合接什么活，又有哪些活暂时别急着交？

任务成本从哪省下

先看 Artificial Analysis 的评测。AA 页面显示两者的 Intelligence Index 整数分都是 36。该机构按自己的测试任务估算。Ember 每项约 0.14 美元，Haiku 5.5 约 0.41 美元。0.14 除以 0.41，约为 34%。换成降幅，Ember 的每任务成本约低 66%。

但两者未缓存的输入、输出 token 标价其实一样。每百万输入 0.10 美元，输出 0.50 美元。AA 还指出，Ember 的缓存输入价格更低。每百万约 0.004 美元。在他们的 Agent 测试里，缓存输入占掉不少开销。Ember 也用了大约 Haiku 三分之一的输出 token。AA 估算会受测试设置、推理档位和缓存策略影响。模型或调用方式一变，数字就得重算。不能把 0.14 美元当作固定账单，写进项目预算。

所以，任务成本下降有两个来源。缓存输入更便宜，输出 token 也更少。你拿短问题去测，未必看得见同样差距。Agent 每次调用都带着系统指令、工具说明和前序材料。重复部分有多少，会直接影响缓存能省多少。

这笔账要留在 AA 的测试条件里看。它不是你生产环境的账单。也没算人工审核、失败重跑和接入成本。Meta 官方标价是另一种口径。API 单价不能替代 AA 的每任务估算。两个数字都能参考，但回答的问题不同。

同是编码，测的活也不一样

AA 的 Terminal-Bench 4.0，主要考 Agent 在终端里完成任务。Ember 得 40.9%。Haiku 5.5 得 32.8%。到了 FrontierCode 2.0-AA，测试更接近真实工程。它按改动是否能合并来评判。这里 Ember 是 27.2%，Haiku 是 34.9%。同一个评测机构、同一档推理设置，胜负方向变了。

Meta 官方页面列出的 Haiku Terminal-Bench 是 39.2%，AA 页面则是 32.8%。Meta 标注各模型使用最佳公开 harness。两边数字不同，不能拼成同一张表；下文只比较 AA 同一页面内的数据。

这不是分数互相打架。终端题和工程任务考的是不同环节。前者更像按目标调工具、跑命令。后者还得理解现有代码、改对位置。它要守住项目约束，交出能合并的改动。终端任务跑得完，未必能让它独立接手老项目。

Meta 自己的页面也列了几类内部测试。这些结果不能和 AA 的表格混在一块算。即使先只看 AA，也够得出一个有限结论。总榜适合初筛，不能替你决定每个岗位该用谁。尤其“编码能力”这四个字太宽。终端操作、小函数补全、跨文件重构，不是一项工作。

做 Agent 时，模型要按任务切。别按产品名一刀切。路由、字段提取、带测试的小任务，可拿 Ember 做对照。大范围改动和隐含规则，还不能只凭总分表决定。最终合并也一样。

旧分工这次测什么

我写 Terra 降价时，提过一条办法。挑一份具体工作。让新旧模型用相同材料和验收规则跑。再把失败、回退和人工时间记在这份工作上。那篇还把稿件引用核对列作候选任务。那只是计划，没有完成对照实验。

Muse Ember 这次给这个旧问题多了一份任务画像。先别问“它能不能替代现有模型”。从调用频繁、结果好验收的工作开始。比如核对稿件的日期、金额、产品名和来源材料。结果可以回到原句和出处，问题也能由人确认。写作和最终判断仍由适合的模型与作者负责。

写作流水线有调研、写稿、润色、评阅、配图、分发。不同环节的输入、上下文和验收方式不一样。让某个小模型“负责分发”太笼统。只让它给文章生成标签，条件就很好判断。标签要对应主题，错了也容易发现。让它改稿、生成并发送平台稿，风险和检查成本也不同。

这只是我根据现有流程提出的任务拆分建议。我还没试过 Muse Ember，也没有同一批材料下的对照结果。Meta 和 AA 的数字能提示我测什么，不能替我宣布它在我的文章任务上更快、更省。

你自己怎么给它过秤

先挑一项任务。备好 20 到 30 个真实样本。这个数量只是一个起步建议，不是统计学保证。每个样本用相同输入、提示词和验收标准。分别让当前模型和 Ember 跑一遍。记录通过数、错误类型、重试数、人工修改时间。

测试时固定模型版本和推理档位。再固定缓存、工具权限和重试上限。否则结果差异可能来自配置，不是模型。样本从近期真实任务里抽。标清任务类型和验收结果。失败也要分类。漏字段、误报、改错文件，后果各不相同。

花费也别只记 token。把缓存命中和输入、输出 token 算进去。再把重试、人工修正折算成时间。比较时也别把失败那轮当成便宜完成。把模型费用和返工成本加起来。再除以最终通过验收的任务数。这样算出的是每份合格产物的成本。通过率低，单次省钱，合格交付的成本却可能更高。

AA 只算指定测试的任务成本，不含部署与人工审核。项目上下文、缓存命中率和调用轮次都可能不同。把测试条件固定下来，才有可比的成本记录。

假如 Ember 的 API 费用少了一半，结果却有更多需要重做。那这项任务的总成本未必下降。低风险步骤稳定通过，省下的钱和时间才有收益。

验收条件要写得具体。拿引用核对举例，不能只要求“检查准确”。让它列出稿件原句、来源位置。再核数字、单位和缺失条件。找不到依据时，标为待核。交付后，按同一规则复核。哪些问题报对了，哪些是误报，有没有漏掉关键项。模型跑完不是任务结束，结果过关才算。

如果工作会改代码，测试和代码审查仍要保留。碰线上数据或发送公开内容，最后都得有人确认。小模型分数不错，也不会替你承担出错代价。

总分相同，岗位未必相同

Ember 提醒我们：总分相同，任务能力也可能不同。它在部分 Agent 测试里更省。终端任务成绩也占优。碰到真实工程改动，Haiku 5.5 的成绩更好。这个分岔提醒我们，分配任务得看具体工作。榜单名次不能单独定岗位。

如果你正在搭 Agent，挑一项重复、好验收的活。先做同任务对照。先看它交付是否过关。再看省下的钱够不够抵掉重试和返工。你手上最想让小模型接走的，是什么任务？
