Terra 便宜了，先让它接哪份活

发表于 2026-10-27 分类于 AI 阅读次数： 本文字数： 3k 阅读时长 ≈ 3 分钟
GPT-6.1 Terra 标准 API 输入与输出单价为每百万 token 1 和 5 美元。降价值得试，但迁移应按同一项验收任务记录重试、回退与人工时间；本文核对官方与评测，并记录用 Terra 补充稿件的初次体验，尚未做成本对照。

Hello，我是飞飞。

你每天交给 Codex 的活，有哪一份值得换给 Terra？OpenAI 刚把这档模型更新了。价格往下走，电脑操作也是主打。看着挺诱人，但我更想先替一份具体工作找个新选择。

让它竞争一份活，失败和换回强模型的消耗也记在这份活上。 这样才知道，便宜有没有落到手里。

写完初稿后，我把 Codex 切到了 GPT-6.1 Terra，让它补充这篇稿件。眼下有一次真实使用过程，但还没有新账单和同任务对照。上周聊缓存，算的是重复输入怎么收费。这次换个问题：一份工作，该由谁来做完？

便宜的是哪一项

截至 10 月 27 日，官方价格表里，标准 API 每百万 token 的价格是：

模型 普通输入 输出 缓存读取
GPT-6.1 Sol 2 美元 10 美元 0.10 美元
GPT-6.1 Terra 1 美元 5 美元 0.05 美元

token 是模型计算文字等内容用的单位。这三列，Terra 都是 Sol 的一半。对反复调用的项目，这个变化很实在。

但你接的是 API，还是在 Codex 里用套餐？得先分开。

发布说明说，Codex 和 Work 的同一份套餐额度，用 Terra 可以覆盖更多任务。这里不能套 API 单价，算成月费也减半。包月费、额度消耗和按量账单，各有各的记录。

价格表也有适用条件。模型文档写明，输入超过 272K token，整次请求的输入与缓存费翻倍，输出费乘 1.5。能装很长的材料，和按普通单价处理，是两件事。

缓存写入另有价格，Fast 等服务档也不同。我会先把模型、服务档和输入长度记下来。免得拿一次短请求的价格，去估整天的长会话。

评测给了什么答案

这次有第三方材料，不能只剩一句“便宜还得自己测”。

Artificial Analysis 的评测里，最大推理档的 Terra，相比上一代，智能指数高了 6 分。该评测的每任务成本，从 1.40 美元降到 0.40 美元。

这个结果值得认真看。它说明在那组题、那种设置下，能力提高的同时，任务成本确实降了。价格降低并没有被更多消耗全吃回去。

不过，这组“每任务”对应的是评测里的题。它不能直接变成“我的网页操作也只花原来的三成”。你我手上的活，还没跑进这份报告。

另一个细节更影响日常选择。AA 的智能指数里，低、中推理档站在成本效率前沿。到了编码智能体指数，站在前沿的是低档和 xhigh 档。前沿是什么意思？在这组评测里，其他选择没法同时更便宜、得分更高。

所以我不会把“推理开到最大”当通用省心按钮。模型愿意多想一会儿，得换来这份活更容易验收，才值得。

官方也留了边界：最复杂的编码任务，Sol 和 Astra 仍是更好的选择。电脑操作的提升，不能顺手翻译成“重构老项目也该全换”。

我的旧分工要改哪儿

这事能接上我七月的模型分工记录。

那时我的写作流程已经分了轻重。写稿和润色交给强模型。排版、标签分类这些工作，我手动换便宜的模型。更早那篇 Cursor 笔记还写过，我曾什么任务都用 Opus，看到账单才改策略。

七月文章里，我对格式处理说得挺满，觉得便宜模型“错不到哪儿去”。现在再看，这句话该收窄。内容少了一段、链接换错了，格式再整齐也交不了。

现在这套流程，公众号拆段已经有固定脚本。它会保护链接和加粗标记，再按句号拆段。这样一件规则明确的活，我没必要为了用新模型，改成让它看着编辑器一段段点。

我更想试的是引用口径核对。把一份稿件和原始材料交给它，找数字、单位、适用条件有没有写丢。这需要理解句子，脚本搜到同一个数字，还判断不了这句话用得对不对。

也不能把整条写作流水线一起搬过去。调研时核引用、写稿时选观点、排版时保留文字，要求不同。整篇出了问题，若不分环节，根本说不清是哪个选择让成本涨了。

先保留现有脚本和强模型，只换一个环节。这样即使试得不顺，也能知道该把哪一步换回来。

Terra 的模型文档还写着，工具调用要走 Responses API。对自己接接口的人，换模型名只是其中一步。原来的工具定义、返回结果和失败处理，都得沿着实际入口再验一遍。这里增加的接入工作，也不能藏在“模型更便宜”后面。

电脑操作尤其要把终点说清。核一份文档，终点可以是一份带位置的检查报告。改一个页面，终点还包括保存后的文件和能打开的预览。它点完按钮，你就停下计时，后面的确认便漏了。

这份待测任务，我会直接这样写：请核对稿中引用，只交检查报告，不直接改稿。每条列出稿中原句、来源位置、遗漏条件和修改建议。找不到出处就标待核，别猜。报告里的问题，我逐条回原文确认。

切到 Terra 的这一回

这篇初稿写完后，我在 Codex 里切换到 GPT-6.1 Terra，交给它的任务很具体：把这次使用经历补进文章，并让相关平台稿跟上修改。

它先读了文章和现有平台稿，发现原文还写着“我还没用过新版”。这句话和我刚切换模型的事实已经对不上，得改。公众号和知乎版跟着正文同步，小红书、知识星球和 X 的短稿也要各自更新，不能只修博客正文。

这一次可观察到的是稿件修改和文件校验。此前的选题、调研、初稿、评阅和配图，不能因为我现在切了模型，就全部算成 Terra 跑的。当前也没有拿同一任务跟 Sol 对照，完成时间、额度和返工次数都没有可比记录。

所以这条体验能证明我已经在写作流程里开始使用 Terra，也留下了一个具体任务。它能不能比原来的选择更快、更省，仍要等同条件对照。

一份活怎样记账

如果你也想试，先写一句怎样算做完。

拿引用核对来说，报告要能回到具体原句。它报的问题是否成立、关键条件有没有漏，我都要查。多报一堆不存在的问题，也会增加工时。只说“检查完成”，不算合格。

同一份原稿、同一套规则，分别交给现用模型和 Terra。工具入口也尽量保持一致。两边若连材料都不同，就先记体验。省了多少，先别急着报。

我准备把记录缩成这些栏。现在仍是待测表，数值留空。

记录项 怎么记
任务编号与验收 一份材料对应一个编号，先写合格条件
模型与设置 模型名、推理档、服务档、工具入口
调用费用 首次、重试、换模型后的调用合计
人工检查 查漏、改错、接手处理的分钟数
结果 独立合格、回退后合格、人工完成、失败

两条路线分开记：现用模型直接做；Terra 先做，必要时换回强模型。API 费用各自合计，各除以这条路线最终由模型交付、验收合格的任务数。失败消耗留在各自分子里。人工接手完成的另列，不放进模型交付数。没有合格任务，这个比值就没法算。

换回 Sol 才做完的，沿用原编号。Terra 前面的消耗不能清掉。同时单列 Terra 独立合格了几份，回退才合格了几份。路线跑通了，不等于 Terra 单独就能干好。否则表会很好看：便宜模型总是很省，接手的人总是很累。

人工分钟单独看，别随手折成美元，装成精确利润。对独立做项目的人，晚饭后能用来开发的那一小时，本来就很有限。

若用 Codex 套餐，我会另记额度变化和任务耗时，不拿 API 价冒充实际扣费。任务没跑完，额度窗口又重置了，就把这次比较受干扰写出来。

先试这一份

说实话，新模型又便宜又能干，直接换掉主力很有吸引力。天天手动切模型，也烦。

但我更愿意先给 Terra 一份边界清楚的工作。能用脚本稳定完成的继续跑脚本；要试的环节，留下同一份输入、产物和验收记录。它多快、少花多少、要不要人接手，都围着同一个任务看。

若它少花额度，却让我来回核三遍，迁移就先停在这一环。若合格结果稳定、检查时间也没增加，再考虑交下一份工作。

这次降价已经发生，评测也给了值得尝试的理由。我自己的省钱结果还欠着。等真跑完一份活，再报。

如果先做引用核对，你最怕它漏掉哪一种：单位、日期，还是适用条件？
