给智能体放权，别赌它的人品：OpenAI 怎么用操作系统把 Agent 关在笼子里

发表于 2026-11-19 分类于 技术 阅读次数： 本文字数： 3k 阅读时长 ≈ 3 分钟
终端命令确认十次有八次是闭眼回车。OpenAI 披露 Codex 本地沙箱架构：用 macOS Seatbelt 与 Linux bwrap 把防线焊死在系统内核。

Hello，我是飞飞。

如果你日常也开着命令行 Agent 写代码，我想先问你一个极度真实的问题：每次终端弹出一行执行命令的黄色警告时，你真的会逐字看清那串参数再敲回车吗？

老实交代我自己的底细。十次里面有八次，我其实只是抬眼扫一下命令的大致形状，只要没看见直接的格式化或者删除主目录指令，手指就下意识敲了回车。开着自动化流水线跑长任务时，这种审查疲劳尤其明显。遇到报错让它看着修，它一口气执行几十条命令，真要逐行核对它临时拉回来的脚本和系统调用，绝大多数人都没有这份定力。也正是这份没有定力的偷懒，把那道本该由人来守的闸口，悄无声息地让了出去。

自动化最昂贵的代价，往往就藏在没有人盯着的时刻。

这几天 OpenAI 发布了一篇很长、甚至有点枯燥的工程博客，标题叫《Inside the Codex sandbox》。作者是技术主管 Michael Bolin。全篇没有任何玄乎的模型新能力演示，翻来覆去只讲了一件事：当他们把 Codex 放到用户的本地终端直接跑命令时，他们到底是怎么用操作系统的底层机制，把这个手里握着真实系统调用权限的智能体，稳稳关在笼子里的。

读完这篇长文，我心里最大的感触是：业界终于开始从靠人品防翻车，转向靠操作系统内核焊死防线了。

虚拟机太重，纯靠自觉太险

面对智能体越界的风险，过去的工程圈通常只有两条极端路线。

一条路线叫信任防线。它指望靠系统提示词的约束、大模型的对齐，或者在终端给用户加一个必须按回车的弹窗。但天天用 Agent 的工程师都知道，这道防线脆弱得像一张湿透的卫生纸。模型会用一种特别合理的语气干出极其离谱的事情。遇到 prompt 注入、带毒的开源仓库，或者长任务上下文压缩带来的目标漂移，Agent 会极其笃定地觉得把代码抄送出去、改动全局配置是当下最高效的解法。至于人工弹窗，只要频次超过承受阈值，人眼审核就退化成了无意识的回车放行。

另一条路线叫彻底绝缘。既然本地危险，那就把 Agent 关进完全干净的 Docker 容器或者远端临时虚拟机，干完直接销毁。听起来很安全，可在真实的工程世界里，这条路能把开发者逼疯。

你在本地写移动端项目，需要用到本地模拟器；你在调系统驱动或硬件通信，需要真实的串口；或者项目依赖了复杂的本地编译链与私有凭证。一旦把 Agent 扔进干净的远端容器，你手头大半任务立刻因为环境缺失而瘫痪。为了安全，直接把工具最值钱的上下文和生产力丢掉了。

这就是为什么 OpenAI 的工程师在文章里明确立下了一个原则：留在宿主机上，但系紧安全带。

他们既不想为了安全把开发者赶出熟悉的本地开发机，也绝不肯把整台机器的生杀大权托付给 AI 的推理自觉。唯一的出路，就是把安全防线从应用层彻底往下沉，下沉到操作系统内核的强制访问控制。

三大系统给进程系上安全带

很多人以为做沙箱就是简单给命令加黑名单，比如拦截某个特定的危险指令。但在真实的 Shell 环境里，绕过字符串黑名单的技巧有上千种。

OpenAI 在 Codex 里的做法非常克制。它没有重复造一套虚拟化的大轮子，而是把当前三大主流操作系统的原生隔离能力挖到了极致。

在苹果 macOS 系统上，Codex 直接启用了底层的 Seatbelt 框架。熟悉苹果系统的开发者对这个名字不会陌生，它正是系统工具所依赖的 Mandatory Access Control 强制访问控制基石。通过声明式的规则配置，Codex 可以在子进程启动的瞬间，向内核注入一套不容妥协的写操作白名单。

无论 Agent 生成的脚本写得多花哨，无论它用哪种冷僻的系统调用试图摸一下敏感路径，只要目标不在当前工程的工作区目录内，操作系统内核就会直接抛出拒绝访问的硬错误。你的系统主目录、钥匙串、敏感凭证目录，在内核眼里对这个进程是彻底不可写的。

到了 Linux 和 WSL 环境下，OpenAI 采取了组合拳：Bubblewrap、seccomp 以及 Landlock。

在 Linux 里最麻烦的问题是，普通开发者跑命令不会随时带着 root 特权，而传统的很多隔离手段往往需要系统级守护进程。Codex 借助 Bubblewrap，在非特权用户空间下利用 Linux 命名空间机制，为子进程捏出一个只有必要文件系统挂载的虚拟视图。紧接着，利用动态编译的 BPF 过滤程序挂载到内核层，拦截未授权的底层系统调用；再配合现代 Linux 内核提供的 Landlock 模块，把文件系统的读写路径牢牢钉在当前项目的目录树上。

至于在 Windows 平台，他们则使用了受限令牌与专门生成的合成安全标识符。通过在进程令牌里剥离管理员权限和特权组，给每一个运行实例分配独一无二的受限身份，并结合文件系统的访问控制列表，确保生成的执行进程即便被恶意脚本操纵，也绝没有可能越过当前分配的工作目录半步。

防线的裁判不再是那个有时候会犯迷糊的大模型，也不是那个随时想按回车跳过的程序员，而是冷冰冰、没有情绪波动的系统内核。

只锁磁盘，网络出站更险

把文件系统的写入权限锁进当前目录，一个本地 Agent 就算真正安全了吗？

答案依然是否定的。只要网络通道是完全敞开的，危险的隐患就只被堵住了一半。

设想这样一个场景：你让 Agent 分析一个刚拉下来的开源项目，项目里暗藏了一个带毒的第三方依赖。Agent 在本地分析代码、安装环境时，该依赖在后台偷偷读取了你的环境变量，并且用一条极其普通的网络请求，把刚才拿到的敏感信息打包发送到了攻击者的公网服务器上。在这个过程中，磁盘上的敏感系统文件没有被修改，但你的隐私和凭证已经顺着网络出站口流了个精光。

OpenAI 这次在长文里特意强调了网络沙箱与出站代理的设计。

在 Linux 上，他们通过网络命名空间切断了子进程直连外部网络的可能；在其他平台上，则结合了系统的网络规则与统一的出站代理服务。

这个出站代理就像守在门外的海关检查站。默认状态下，Agent 发起的任何外网请求都会被无差别阻断。只有当任务明确需要拉取依赖时，系统才会按照预设的白名单规则，放行被认可的官方依赖源与特定服务地址。非白名单的任意网络尝试，不论是常规的端口连接，还是伪装成 DNS 查询的隧道通信，都会在代理层被立刻掐断并记录警报。

把磁盘写权限限制在工程目录，把网络出站卡死在白名单内。两道枷锁合拢在一起，才算把一个在宿主机上自主跑命令的智能体，真正变成了关在透明防弹玻璃后面的机械臂。

把刹车踩在内核，不赌自觉

我之前在写自己给 Agent 收紧钥匙的复盘时，曾经总结过一句话：默认放心让模型去想，但谨慎放行让模型去做。想是免费的，做是有后果的。

当我们在日常工作流里越来越依赖 Agent，当流水线里的工具调用从一两步扩展到几十步，人去肉眼盯梢的成本就会呈几何级数上升。在这个时候，任何基于自觉的假设，最后都会被人类自身的惰性击穿。

OpenAI 披露 Codex 沙箱架构的价值，不在于展示他们用了多么炫酷的前沿科技。恰恰相反，他们用的全是操作系统里躺了多年的原生工具：macOS 上的安全规则、Linux 里的命名空间和过滤机制、Windows 的访问控制。

这给所有正在搭建自己的 Agent 系统、正在把命令行执行权交给 AI 的开发者提了个醒：我们不能一边享受着全自动化的快感，一边在心里默念它不要出错。

给智能体最好的放权，从来不是毫无保留的信任，而是用确定性的系统规则，替它把悬崖边缘的护栏修得足够坚固。当护栏在内核层焊死的那一刻，我们才敢真正放开手脚，让它在工作区里尽情奔跑。
